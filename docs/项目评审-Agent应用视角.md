# 「矿山智工 · 设备健康智能体」评审报告
> 评审视角：Agent 应用（scene#17）· 2026-09-24

---

## 一、总体评价

**结论：这是一个工程完成度和可信度设计都显著高于同类参赛作品的「受约束智能体」应用，但在「Agent 自主性」维度上有意做得很克制——这既是它最大的优点，也是评审场上最可能被质疑的点。**

综合评分（Agent 应用视角）：

| 维度 | 评分 | 说明 |
|------|------|------|
| 工程完成度 | ★★★★★ | 9 条验收命令、三层测试矩阵、故障注入断言，远超一般参赛作品 |
| 可信 AI 设计 | ★★★★★ | 规则引擎出数字 + LLM 只润色 + 数字不变量出口校验，是真正的差异化 |
| 安全与隐私 | ★★★★★ | 三重进程隔离、IPC sender 校验、零联网零 key、备份校验 |
| Agent 自主性 | ★★★☆☆ | 7 类意图靠正则规则、无规划/多步任务链、LLM 不参与决策 |
| 交互体验 | ★★★★☆ | 确认卡、歧义必问、可撤销、操作留痕——human-in-the-loop 范式教科书级 |
| 可扩展性 | ★★★☆☆ | appStore 1296 行巨型单体（域化迁移已在规划中） |

### 1.1 最值得肯定的三点

1. **「大模型的失败模式是少说，不是说错」——这是全场少见的正确取舍。**
   大多数 Agent 应用把 LLM 推到前台做计算和决策，本项目反其道而行：`verifyNumbersSubset()` 出口校验保证生成文本中的每个数字 ⊆ 规则引擎给出的数字集合，任何一环失败静默回退。这个模式可以直接写进答辩 PPT 的第一页。

2. **写库权限的安全设计是完整的工具调用（tool use）安全范式。**
   `nlCommand.js` 的三原则（不猜/不静默/可审计）+ 歧义候选让用户选 + 执行前预检 + 确认卡 + 一键撤销 + 操作日志落库——这就是标准的 human-in-the-loop agent 工具调用链路，且每一步都有 e2e:nl 覆盖（含"纯查询不误写"的反向断言）。

3. **文档的诚实性罕见。** README「已知边界」一节如实列出撤销栈仅内存、操作日志滑动窗口、语音/OCR 为演示样例等 20+ 条限制，且解释了为什么。这在评审时是信任加分项。

### 1.2 主要短板（按风险排序）

1. **「Agent 含量」答辩风险（最大风险）**：意图识别完全靠手写正则（`INTENT_RULES`），LLM 不参与任何决策。评委若问"这和 2015 年的规则系统 + 一个润色器有什么区别？"，目前的答案不够有力。
2. **检索层无语义能力**：知识库检索是关键词 + 同义词手写打分（标题+12/分类+4/…），“挖机水温高”能命中是靠同义词表穷举，换个说法就漏。
3. **撤销/审计的持久性缺口**：撤销栈存闭包、仅内存；操作日志非全量且部分写入类别不记日志。这两条同根同源——缺少一个可序列化的事件层。
4. **单机规模天花板未验证**：sql.js 全内存加载，60 台设备演示流畅，但万台级台账、数年维保记录下的表现无数据。
5. **核心卖点入口是模拟的**：「口述录入」的"口述"实为打字（ASR 未实现），演示时若被追问"现场工人怎么用"，只能承认是演示样例。

## 二、优化建议

### P0 · 赛前必做（直接回应"Agent 应用"赛道的评审关切）

**1. 给意图识别加一条「LLM 兜底通道」，而不是替换规则引擎。**
规则优先、置信度低时降级到本地 LLM 做意图分类 + 槽位抽取，输出强制过 JSON Schema 校验 + 既有确认卡。规则引擎保底不变，LLM 只扩大覆盖面——安全叙事完全保留，但可以回答"这就是 Agent"：*规则是白名单，LLM 负责长尾，出口校验兜底*。这比现在"0.5B 只会复述"的叙事强一个量级。
落点：`nlCommand.js` 增加 `parseWithLlm()` 备选路径；1.5B 档（升级规划 3.1 已规划）启用。

**2. 把 7 类意图形式化为「工具注册表」。**
现在意图/动词/执行动作散在 `nlCommand.js` + `nlActions.js` 中。定义统一的工具描述（名称、参数 Schema、预检规则、逆操作），确认卡直接由 Schema 渲染。好处：① 为 LLM function-calling 铺路；② 撤销可序列化（见下）；③ 域化架构迁移时工具自动随域注册。

**3. 补一条「多步任务链」演示**：如"今天 3 号、7 号、12 号挖掘机都巡检完了，有问题都建单"——一次口述生成 N 张工单的操作计划清单，整批确认。这是评委能直观看到的"自主规划"，且复用现有确认卡范式，工作量 2-3 天。

**4. 语音入口最小真实化**：接入 sherpa-onnx / whisper.cpp 本地中文 ASR（几十 MB，离线合规），哪怕只覆盖报故障一类意图。让「口述录入」角标从「演示样例」变成真的，这是演示冲击力最大的一笔投入（升级规划批次 3 已规划，建议提到赛前）。

### P1 · 结构性改进（赛后 1-2 月）

**5. 撤销持久化 = 事件溯源，一石二鸟。**
把闭包式撤销改为可序列化的逆操作描述（op-log / event sourcing），同时解决：① 撤销跨刷新失效；② 操作日志非全量、部分类别漏记——事件日志本身就是审计日志。与 P0-2 的工具注册表天然配套（每个工具声明自己的逆操作）。

**6. 混合检索：关键词打分 + 本地向量检索。**
用 bge-small-zh / Qwen3-Embedding-0.6B（量化后 ~100-300MB，ONNX 或 llama.cpp embeddings，纯离线）对知识库 + 手册切片建索引，与现有关键词打分做 RRF 融合。手册库（36+32+18 页）问答质量会明显提升，且不破坏"查不到就说查不到"的原则（可加相似度阈值）。

**7. 数字不变量扩展为「实体不变量」。**
`verifyNumbersSubset()` 只校验数字。补一层实体校验：生成文本中的设备名/型号/日期/状态词必须 ⊆ 输入事实集合，防止 0.5B 复述时把"3 号机"说成"13 号机"。实现成本极低（复用同一模式），可信叙事更完整。

**8. 单机规模压测数据**：生成 5000 台设备 + 5 万条维保记录的数据集，实测首启播种、落盘、看板加载、检索延迟，把数据写进 README 和答辩材料。若有瓶颈，虚拟滚动（已有 `virtualGrid.js`）+ 分页加载即可补。

### P2 · 工程与体验

- **视觉回归自动化**：README 已承认"视觉层靠人工过截图"。用 Playwright 截图基线对比（深浅两主题 × 16 路由），把对比度审计之外的最后一块人工验证补上。
- **首启骨架屏**：播种 60 台 + 导入 3 本手册期间界面空白，加骨架屏或进度提示。
- **浏览器模式备份导入修复**：`importBackup()` 调用点缺文件内容参数，属已知 bug，修复成本低。
- **Element Plus 按需引入**（升级规划必修项 #1）：vendor 974KB 是首屏最大块，配合 `unplugin-vue-components` 一次解决。
- **CSP 注入 + IPC sender 校验**（必修项 #2）：README 声称"每个 ipcMain.handle 都做来源校验"，若升级规划审计发现的"未校验 sender"仍存在，这是文档与代码不一致的风险点，赛前必须对齐。

### 不建议做的（维持既有克制）

- 不要为了"更像 Agent"让 LLM 参与数值计算或直接写库——现有"规则出数字、LLM 说人话"的边界是项目最硬的资产，所有增强都应在这个边界**之内**做（LLM 兜底意图、工具 Schema、批计划确认都符合）。
- 云端多端同步、微调、数字孪生等升级规划中已"明确不做"的方向，赛前不要动摇。

## 三、使用体验（UX）专项评审

### 3.1 做得好的

| 方面 | 现状 |
|------|------|
| 信息架构 | 侧栏 5 分组 15 入口，按业务动线组织（设备健康→运维执行→AI 智能→数据资产→系统），新用户可循主线走通 |
| 反馈与空态 | `v-loading` / `el-empty` / 加载中覆盖 11+ 个视图；落盘失败明确报"保存失败"并保持脏状态可重试——不骗用户 |
| 无障碍 | WCAG AA 对比度门禁跑浅色+深色双主题、16 条路由；深色主题全量令牌覆盖，不是摆设 |
| 引导体系 | 12 步引导演示（默认手动推进、可切自动、首启只弹一次）+ 演示工具条；#29（下拉 0×0 打不开）、#30（暂停键失效）已修并用真实鼠标事件回归 |
| AI 交互范式 | 理解卡确认、歧义点选、预检拦截、一键撤销、流式输出（onChunk）、QuickQuestions——写库类 AI 交互的完整范式 |
| 动效克制 | GSAP 只用于数字滚动等必要交互，ECharts 按需异步加载，首屏不为它付下载 |

### 3.2 体验短板（按刺眼程度排序）

1. **首启白屏无反馈**：播种 60 台设备 + 导入 3 本手册期间界面空白，只有"已知边界"里一句话承认。这是第一印象的最差点。
2. **「口述录入」名不符实**：没有 ASR，"口述"= 打字，界面上还打着「演示样例」角标——现场演示时这是最容易戳穿的体验断点。
3. **撤销按钮"可见但不可用"**：刷新后按钮仍显示，点了才明确拒绝并解释。诚实的初衷好，但用户感知上更像 bug；应置灰 + tooltip 说明，而不是可点后拒绝。
4. **无键盘效率工具**：Ctrl+K 命令面板在规划中被移除（`registry.js` 注明），全局搜索也没有快捷键唤起。高频用户（一天建几十张单的现场工程师）每个动作都要点鼠标。
5. **窄屏体验差**：<1200px 全部回退横向滚动，无响应式列隐藏。演示用大屏没问题，但一线工程师常用 13 寸笔记本/分屏。
6. **一次只处理一件事**：确认卡、歧义点选都是单条交互，"3 号、7 号、12 号都出问题了"这类批量口述没有 UX 承接——每台设备都要走一遍完整流程。
7. **0.5B 叙述的等待感**：纯 CPU 生成、maxTokens 128，叙述短但慢机器上仍有可感延迟；无"跳过润色"开关，也无润色缓存（同一结论重复生成）。

### 3.3 UX 优化建议

> **实施记录（2026-09-24）**：P0-1、P1-2（部分）、P1-3（开关+缓存）已落地，全量验收通过（lint / self-check 332 / main-check 17 / store-check 20 / coverage / build / e2e 116 / e2e:nl 28 / 对比度）。
> - 首启闪屏：`index.html` 静态闪屏 + `utils/bootSplash.js` 分步进度（开库→播种→导手册→加载界面），挂载自动消失；
> - 窄屏：`utils/responsive.js`（1200px 断点），工单表隐藏工单号/类型/来源/创建时间，备件表隐藏类别/单价/流水来源；
> - 叙述层：AI 助手头部「模型润色」开关（关闭即静默跳过，不插降级块）+ 叙述结果 LRU 缓存（50 条，同一结论秒回）。

- **P0-1 首启进度反馈**（半天工作量，第一印象收益最大）：骨架屏或分步进度提示（"正在播种演示数据… / 正在导入随包手册…"）。
- **P0-2 撤销按钮状态修正**（1 小时）：刷新后置灰 + tooltip"刷新后撤销不可用"，把"诚实的拒绝"变成"诚实的外观"。
- **P0-3 Ctrl+K 命令面板恢复落地**（规划文档已有完整设计 `docs/tasks/12-CtrlK命令面板.md`）：导航/动作/查询/AI 四类命令，是效率体验的最大单点提升；顺带给全局搜索绑快捷键。
- **P1-1 批量操作计划卡**：一次口述解析出 N 条操作 → 清单式计划卡整批确认（与评审报告 P0-3 的多步任务链是同一件事的 UX 面）。
- **P1-2 窄屏响应式**：把工单表已做的"关键列前移"扩展为通用列优先级机制，次要列自动隐藏而非全部横向滚动。
- **P1-3 叙述层体验**：加"跳过润色/直接显示结论"开关；对相同结论缓存润色结果；生成中显示明确的流式打字态（已有 typewriter.js，可复用）。
- **P2**：评委模式（大字号 + 时间锚点的大屏线，升级规划 4.2 已设计）；操作日志补齐备件/设备增改两类缺口，让"可审计"在界面上无裂缝。

## 四、答辩建议（一页话术）

**如果被问"这算 Agent 吗"：**
> "这是一个**受审计约束的智能体**。它有感知（多源数据导入）、决策（7 类意图 + 6 级指代消解 + 歧义主动询问）、行动（建单/扣件/归档/复诊闭环）、记忆（知识库自沉淀 + 故障案例自动提炼）——完整的 Agent 环路。区别在于：工业现场不允许黑盒试错，所以它的每一次写库动作都必须可预检、可确认、可撤销、可审计。**自主性以可信为界**，这是我们和'演示级 Agent'的本质区别。"

**三个必演示动作**：拔网线 → 口述建单并当场撤销 → 问一个知识库没有的问题看它说"查不到"。
