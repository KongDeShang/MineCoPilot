一立场定位

定位不是"我们做了什么"，而是"我们选择站在哪一边"。下面三条立场，决定了后面所有的功能取舍。

立场一：数据的主人是矿上

工程机械行业有一个长期存在的矛盾：厂家想知道自己卖出去的机器怎么坏的，矿上不愿意给。

  • 矿上的顾虑是真实的：维修频次与费用反映管理水平，影响二手机残值，出事故时还是责任证据。
  • 厂家的诉求也是真实的：不知道"人怎么修的"，产品改进就只能靠经销商转述和召回。

本项目在架构上站在矿上这一边：数据从设计上就不出本机。

  • 无任何对外网络请求，无任何云端 API Key（唯一例外是开发模式加载本地 Vite 服务）
  • 数据落在本机 SQLite 单文件，.mbak 一键整库导出，随时可搬走
  • 共享是客户的选项，不是产品的默认行为

这不是技术限制（"我们上不了云"），是设计选择。

现实参照：约翰迪尔曾用软件锁限制农民访问自有农机的数据，引发全美 Right to Repair 运动，多个州立法限制。数据归属上站错边，用户会反抗，然后立法介入。

立场二：用回报替代法规

维修记录为什么留不下来？不是没有工具，是没有动机。

  • 航空业的维修数据是完整的 —— 因为适航法规强制要求，不记飞机不能放行。
  • 矿山没有这条法规，所以只能靠回报。
  • 更具体地说：需要记录的是矿上，动手的是工程师，而工程师从中得不到任何东西。

本项目把"回报"放进产品本身：口述一句话，当场拿到处置结论；记录是这件事的副产品。

现实参照：2009 年美国 HITECH Act —— 政府发现医生就是不用电子病历，结论不是"系统不够好"，而是直接补贴。光有系统不够，必须让人有回报。

立场三：可审计优先于更聪明

小参数模型（0.5B）直接做数值推理不可靠，会自信地编出一个看起来很像的停机损失。

本项目的取舍是：不让它算。所有数字由确定性规则引擎产生，模型只负责把已核实的结论改写成口语中文；出口处两道校验，不通过就整段丢弃、回退原文。

大模型的失败模式是"少说"，不是"说错"。

这条立场的代价是放弃了"模型更聪明"的叙事；收益是每一个数字都能倒推回台账，而这是矿山决策场景的硬要求。

我们的语言：一个老师傅

三条立场在向用户表达时，收束为一个隐喻：

矿山智工做的，是一个走不了的老师傅

矿山的经验，一直存在一个人的脑子里。它能解决几乎所有问题，唯独解决不了两件事：他会退休，而且他只有一个。

已有功能在这个隐喻里的角色
健康评分 / 体检报告他给机器做体检
设备病历他记得每台机器的病史
故障案例库他见过的病例
维修规程库他的经验
告警中心 / 维保日历他提醒你该管哪台
口述录入你跟他说话，不用填表
复诊管理他记得回访
操作日志 + 身份他认得是谁在干活
必须如实说明

这是一个界面隐喻，不是技术声明。系统不声称有人格或意识。它的"关心"目前以告警中心与数据看板的形式呈现，尚未做到开机主动提示（见「五 能力边界」）。它的"记性"就是那份数据库。

它和立场三是同一件事的两面：老师傅最大的美德是"他说的话你信"；而本项目让每句话都能被追问"凭什么"并答得上来 —— 一个说不清依据的老师傅，没人敢信。

三能力详解

逐项说明"做了什么、怎么做的、为什么这样做"。

3.1 数据整合：把三份格式不同的 Excel 变成一本台账

能力：一次拖入多份表头写法不一致的 Excel，自动对齐合并入库。

  • 14 个标准字段映射（设备名称 / 型号 / 购置日期 / 状态 …）
  • 两轮表头识别：先精确匹配，再模糊匹配（"设备名称"/"名称"/"机器名" 归一到同一字段）
  • 内置 5 份格式各异的示例模板（设备清单 / 维保记录 / 巡检记录 / 配件库存 / 资产表），可一键下载对照
  • 导入前预览与校验，异常行明确报出

为什么这样设计：现场的真实情况是生产部、采购部、维修部各发一份表，表头各写各的。要求客户先统一格式，等于要求客户先做一遍我们已经做的事。

3.2 健康评估：可解释、可复算、不掩盖现场事实

能力：给每台设备一个健康分，且这个分数每一步都能倒推。四个因子（src/renderer/src/utils/health.js）：

因子规则扣分上限
维保及时性每超期 1 天扣 2 分；无维保记录扣 30 分≤ 45
设备机龄超过 5 年后，每多 1 年扣 5 分≤ 45
故障状态当前处于故障状态扣 30 分—
数据完整度购置日期 / 上次维保 / 设备型号 每缺一项扣 5 分—

分档：A ≥ 85 ｜ B 70–84 ｜ C 55–69 ｜ D < 55

强制升级（不允许"分数好看"盖过现场事实）：

  • 维修超期 > 30 天 → 至少 C 级
  • 维修超期 > 45 天 → 至少 D 级
  • 处于故障状态 → 直接 D 级

每个因子同时输出 {扣分, 计算式, 数据来源}，界面上与导出的体检报告里都能看到完整算式，例如：

距上次维保 140 天 − 周期 90 天 = 超期 50 天，每超期 1 天扣 2 分 → 扣 100 分，单因子上限 45 分，实际扣 45 分。

停机损失测算（公开公式）：风险系数 × 日产出 × 预估停时，日产出按机型取值（矿卡 12 万 / 天、破碎机 9 万 / 天、挖掘机 8 万 / 天）。场景预设：3 种矿种的风险参数可切换，改参数后全量重算。

3.3 自然语言作业：一句话变成一张工单

能力：工程师说人话，系统完成设备定位、意图识别、预检、建单。

  • 7 类意图：报故障 / 完成工单 / 记录维保 / 改设备状态 / 做复诊 / 新增知识 / 查询
  • 设备指代 6 级匹配：全名 → 简称 → 编号 → 序号 → 型号 → 模糊，逐级降级
  • 歧义必问：指代不唯一时列出候选，确认按钮置灰，拒绝在有歧义的情况下写入
  • 写库前预检：例如"完成工单"会先查该设备是否真有未完成工单，没有则拦截并说明
  • 理解卡：写入前展示"将要发生什么"（新建工单 / 归档病历 / 生成复诊 / 扣减备件），确认后才落库
  • 一键撤销：撤销栈跨刷新持久化（最多 20 步），带 CAS —— 写入后又被改过的记录拒绝自动回退，不做静默覆盖

能力覆盖矩阵：npm run coverage 专门枚举口述指代消解的各种说法（明确不是代码覆盖率），让"说得不一样也能认对"这件事可验证。

3.4 知识检索与问答：先查台账，再查规程，查不到就说查不到

能力：回答设备相关问题时，先查真实台账数据，再检索本地规程库，未命中时明确说"没有检索到"并列出覆盖范围。

  • 规程库：30 条 / 12 分类 / 34 组同义词；相关度打分检索，非关键词硬匹配
  • 图谱增强：同义词扩展与文本相关度加权
  • 知识沉淀：同一设备同一系统故障 ≥ 3 次，自动提炼知识草稿，把重复故障变成可复用条目
  • 手册问答：PDF 本地解析，回答带「第 N 页」出处

为什么这条重要：一个会编答案的运维助手，在现场是有害的。"我不知道"是一个必须能说出口的功能。

3.5 本地 AI 与出口校验（本作品的核心机制）

能力：本地大模型把已核实的结论改写成人话，同时保证它说不出任何未经核实的东西。模型规格（src/main/llmEngine.js）：

项值
模型Qwen2.5-0.5B-Instruct
量化 / 体积Q4_K_M ／ 468.6 MB（491,400,032 字节）
推理后端node-llama-cpp，纯 CPU，无需 GPU
上下文 / 生成参数1024 ／ maxTokens 128 · temperature 0.2 · topP 0.9
角色仅叙述层润色，不参与任何数值计算

两道出口校验（src/renderer/src/utils/llmClient.js）：

校验判据拦住什么
数字不变量
verifyNumbersSubset()		生成文本中的每个数字必须 ⊆ 原结论的数字集合模型新造的数字（例如编出一个看起来很像的停机损失）
形状
verifyNarrationShape()		这段文本必须真的在复述结论数字全对但整段答非所问（实测会回反问句、复读提示词、把问题推回给用户）

两条判据分开写、都拦 —— 数字校验管内容，形状校验管"这段话到底有没有用"，结构上互不替代。

失败处理：功能不降级

任何一环失败（模型未加载 / 生成失败 / 数字对不上 / 形状不对）→ 回退到规则引擎原始结论，并在界面上如实说明原因。

  • 模型档位：内置 0.5B；1.5B 为可选下载档位，多源回退（HuggingFace / hf-mirror / ModelScope / GitHub Releases），下载后校验 SHA
  • 装机自检：加载 + 生成 + 校验数字不变量，结果落盘 userData/llm-verify.json
  • 缓存：同人设同原文的叙述结果 LRU 缓存 50 条，避免"同一台设备反复问"时重复生成
  • 可关闭：AI 助手头部有润色开关，关闭后直接展示规则引擎原文 —— 慢机器上避免等待感

3.6 闭环：完成不是终点

完成工单完成
停在这里是多数系统
→
归档写入设备病历
自动留一条维保记录
→
复诊7 天后回访
仍异常则再开工单
→
扣减备件真的少
不是记录，是扣库存

备件联动：维保记录里填写的配件真的扣减库存并留下流水 —— 不是记录"用了什么"，是库存真的少了。知识沉淀：重复故障自动提炼为知识草稿（见 3.4）。

3.7 可审计与留痕

能力：谁在什么时候改了什么，可当场翻看。

  • 操作日志：全部写入留痕并落库，滑动窗口保留最近 500 条
  • 身份：启用应用锁后，每条日志标出操作人；侧边栏底部常显当前身份
  • 应用锁：多账户（姓名 + 4–6 位数字 PIN），PIN 走 PBKDF2-SHA256 + 每账户随机盐，不存明文
  • 空闲自动锁：默认闲置 10 分钟回锁屏（指针 / 按键 / 滚轮 / 触摸都算活动）；可关闭或改为 1/5/10/15/30 分钟，改完当次生效
  • 未解锁不装载业务数据：锁屏状态下主应用根本没被创建，台账数字不会先闪一下

3.9 工程可信度：能力是被验证过的

npm run verify 一条命令按序跑完 10 道，各网专责。

命令管什么

main-check主进程契约：IPC 注册与来源校验、切档失败不得改变当前档位、拉不到远端清单时回退内置
store-check状态层：首启播种闸门、字段白名单回读、落盘失败必须仍是脏状态、重置后撤销栈清空
pack-check打包依赖闭包（运行期依赖有没有被 files 规则排掉、原生库有没有解包）—— 这类缺陷只在装完包才现形
coverage口述指代消解的能力覆盖矩阵
build生产构建

e2e:nl口述录入链路：理解卡 → 歧义必问 → 确认 → 落库 → 刷新仍在 → 撤销 → 纯查询不误写
audit:contrast文字对比度达 WCAG AA（浅色令牌）

断言条数以脚本末行「合计 N 项」为准，本说明书不写死数字。

另有一条不在门禁链里的深色主题审计：npm run audit:contrast:dark（深色令牌下审同样 15 条路由）—— 改深色样式时必须单独跑。

规模压测：npm run bench:scale 在 Node 里真装配 store，灌 5000 台设备 + 5 万条维保。实测满库首启 246 ms、看板重算 56 ms、检索一次提问 22 ms。属"看得见"的规模数据，不是门禁（耗时测量随机器抖动，不该让验收链变红）。

引导演示：右上角一键播放的 12 步主线（看板 → 台账 → 病历 → 工单 → AI 助手 → 规程库 → 复诊 → 本地模型），默认手动点一步走一步、可切自动；首启自动弹一次。

#边界说明
1基于角色的权限分级账户里的"角色"只是标识（界面显示 + 进操作日志），没有"维修工不能删设备"这类拦截
2锁的是界面不是文件userData/*.db 仍可被任何 SQLite 工具直接打开；锁配置在 localStorage，清掉即绕过。防的是旁人随手翻看与误操作，不是技术人员
3日志身份不回填启用应用锁之前写下的日志（含随包演示数据）操作人显示「未署名」—— 那时确实没有身份这回事
4语音识别未实现
5OCR拍照识别为演示用的模拟结果，未接入真实识别引擎
6撤销覆盖范围只有口述录入 / AI 助手的写入可撤销。工单完成、复诊、备件出入库、设备增改、Excel 导入、备份导入都没有撤销
7部分失败不回滚到底撤销逐条执行，失败项会明确报出原因，但已回退的部分不会自动复原
8测点实时数据接入（IoT）未实现。数据来自导入与手工 / 口述录入
9多终端同步 / 企业版私有化部署规划内容，未实现
10本地模型资源占用未实测，仅有"纯 CPU、无需 GPU"的定性结论
11并行写入单机单进程，无并发控制设计
12移动端 / 触摸操作定位为桌面工作台，触摸路径未测
13老师傅的"主动开口"目前以告警中心 + 数据看板形式呈现，尚未做到开机主动提示
14规程检索 ≠ 诊断是"现象 → 规程条目"的匹配，不是诊断。知识库 30 条，覆盖有限，查不到会明说
15档案可被修改库文件未加密，因此维修档案不可作为法律意义上的不可篡改证据
16视觉回归依赖人工，未自动化
