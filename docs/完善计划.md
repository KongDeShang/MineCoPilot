# 矿山智工 · 完善计划（v1.1.x 收敛轮）

> **定位：不扩建。** 本轮不加新功能域，只做一件事——**让「已经宣称的能力」与代码一致**，并补上结构性缺口。
>
> **决策（2026-09-25）**：`docs/升级规划.md` 中的任务 10（数据大屏）、11（多视图）、12（Ctrl+K 命令面板）、13（报告导出增强）、15（语音纪要域）**全部搁置**；模型能力分级**先收敛口径、暂不接线**。
>
> **三条铁律不变**：运行期零联网 / 数据不出本机 / 数字不变量校验。

---

## 一、判据

本轮的验收标准不是"加了什么"，而是这一条：

> **声明的接口没有消费方就不算完成，只算占位。**
> —— 项目自己立的规矩，见 `src/renderer/src/domains/README.md`

按这条判据过一遍当前代码，分两类处置：

- **让它成真** —— 声明有真实价值、代价可控（如手册检索截断、错误边界）
- **把声明改成真的** —— 声明无消费方、或兑现代价远超收益（如模型能力分级、引导演示文案）

两者都是"完善"，且第二类往往更急——**界面上一句没有代码支撑的话，就是把「可审计 AI」的立身之本折价。**

## 二、范围

### 做

| 方向 | 内容 |
|------|------|
| 如实化 | 界面/引导文档里没有代码支撑的表述，改到与实现一致 |
| 真缺陷 | 功能上确实坏了或静默失效的路径（手册检索截断、UI 层吞异常） |
| 韧性 | 错误边界；出错时能看见、能恢复，而不是白屏 |
| 卫生 | 孤儿注释、死导出——回到项目自己定的清理标准 |
| 结构债 | 撤销持久化、日志全量化、分页/虚拟滚动、检索性能 |
| 验证网 | 补上视觉回归自动化，让"靠人过截图"这一层也有基线 |

### 不做

- 升级规划任务 10 / 11 / 12 / 13 / 15（大屏、多视图、命令面板、报告导出、语音纪要）
- 模型能力分级**接线**（本轮只收敛口径；接线作为后续可选项，见 §六）
- 升级规划已"明确不做"的方向：模型微调、传感器接入、局域网多端协同、移动端/扫码、数字孪生/3D、预测性维护

### 三条铁律的自检

本轮所有改动**不新增任何对外网络请求、不引入云端依赖、不绕过 `verifyNumbersSubset()`**。唯一涉及网络的是既有模型下载路径，不动。

### P1-2 手册检索截断修复 + 如实标注

**证据**（三处拼起来才是全貌）：

| 位置 | 内容 |
|------|------|
| `utils/docService/adapters/pdf.js:31` | 切片粒度 = **一页一片**（`chunks.push({ page: p, text })`） |
| `stores/documentDomain.js:34` | `CHUNK_LIMIT = 300`，入库保留前 300 片 |
| `stores/appStore.js:1058` | 检索池只取 `doc.chunks.slice(0, 120)` |
| `views/Documents.vue:29` | 界面显示 `可问答（${row.pages} 页）`——用的是 **PDF 总页数** |

**现状**：**超过 120 页的手册，第 121 页起的正文在 AI 问答里永久检索不到**，而界面上按 PDF 总页数显示"可问答（300 页）"，与实际可检索范围不符，用户无从察觉。两个常量不一致（300 vs 120）本身就是漏改痕迹。随包 3 本手册是 36/32/18 页，全在 120 以内，**演示永远暴露不出来**；导入《资料/》里的真手册（XGT7528A 16.8 MB、XE230_XE250C 12.4 MB）即失效。

**改法**：
1. 检索池取**全量已存切片**（去掉 `slice(0, 120)`，与 `CHUNK_LIMIT` 对齐）
2. 入库时记录 `indexedChunks` 与 `truncated` 标记
3. 界面用**可检索页数**，截断时如实标注"仅前 N 页可问答"

**落点**：`stores/appStore.js`、`stores/documentDomain.js`、`views/Documents.vue`
**验收**：新增 self-check 断言——构造 >120 片的手册，断言全量进检索池、截断标记正确；e2e 手册库文案
**工作量**：0.5 天 ｜ **风险**：低（检索池变大，注意 P2-3 的性能项）

### P1-3 全局错误边界

**证据**：全仓 `app.config.errorHandler` / `onErrorCaptured` / `window.onerror` **零命中**。

**现状**：README 自己写着"模板里调用一个没导入的函数会导致整页白屏"，而防线只有 `vue/no-undef-properties` 一条**静态**规则。运行期任何渲染异常（脏数据、越界取值）都会白屏——**无提示、无日志、无恢复入口**。对现场用户就是"软件坏了"。

**改法**：
- `renderer/src/main.js` 加 `app.config.errorHandler` + `router.onError` + `window.onerror` / `unhandledrejection`
- 错误写入操作日志（复用 `addLog`，`silent` 避免递归）
- 界面给**可恢复**的提示（"这一页出错了，返回看板"），而不是白屏
- ⚠️ 处理器自身不得抛错（否则死循环）

**落点**：`renderer/src/main.js`、可能的 `App.vue`
**验收**：store-check 断言错误处理器存在且能落日志（DOM 层行为由 e2e 观察）
**工作量**：0.5 天 ｜ **风险**：低

#### 细化（2026-09-25 定稿）

**P2-1 撤销持久化** —— 落点 `stores/nlActions.js`（主）、`utils/nlCommand.js`、`views/AIAssistant.vue`、`components/ChatMessage.vue`

> ⚠️ **不动清单冲突已裁决**：逆操作描述只能由 `executePlanItem` 产出，而该文件在"只增不改"清单上。2026-09-25 用户明确授权：**只增 `inverse` 字段，不改判定逻辑**（`undo:` 闭包原样保留）。

现状（实测）：撤销栈是 `appStore.js:1196` 的内存 `ref([])`，条目 `{rawText, summary, changes, undos(闭包数组), at, id}`；`id` 是 `undo-N` 的**每页重排**计数器；跨刷新失效靠 `AIAssistant.vue:254` 的 `CHAT_SESSION_ID` 拦（第一批已把它变成"置灰 + tooltip"，但能力本身仍然只在当次加载内可用）。

六类 `undo:` 闭包（`nlCommand.js`）→ 逆操作描述：

| 意图 | 现闭包 | 逆操作描述 |
|------|--------|-----------|
| REPORT_FAULT (:833) | `removeWorkOrder(id)` | `{op:'remove', table:'work_orders', id}` |
| COMPLETE_ORDER (:873) | 还原工单字段 + 删本次案例/知识条目 + 还原设备快照 | `update(work_orders, id, before, after)` + `remove_many(fault_cases, ids)` + `remove_many(knowledge_items, ids)` + `restore_equipment(snapshot)` |
| ADD_MAINTENANCE (:910) | `revertConsumption(applied)` + 还原设备快照 | `revert_consumption(applied)` + `restore_equipment(snapshot)` |
| SET_STATUS (:930) | `updateEquipment(id,{status:before})` | `update(equipment, id, before, after)` |
| DO_RECHECK (:942) | `updateWorkOrder(id,{recheck_status:'pending'})` | `update(work_orders, id, before, after)` |
| ADD_KNOWLEDGE (:962) | `removeKnowledgeItem(id)` | `{op:'remove', table:'knowledge_items', id}` |

三条设计要点：

1. **带 `after` 做 CAS**。跨刷新撤销的真正危险不是"撤不了"，而是"这条记录之后被别人改过，撤销却照旧把 before 盖回去"（静默改错数据，与 2026-09-17 修的"撤销栈不清导致改错记录"同类）。因此 `update` 类逆操作同时记 `after`，撤销前比对当前值：不等就**拒绝**并说明，不自动回退。
2. **闭包与描述两条路必须给出同一结果**。闭包是当次生效路径、描述是持久化路径，两份实现最容易悄悄漂移 —— 用断言锁住：同一场景分别走两条路，比对结果状态（变异：摘掉 `inverse` 必红）。
3. **持久化预算**。`restore_equipment` 快照含设备整行 + 全部维保记录 + 全部健康快照，单条可达十几 KB。栈上限 20 条写进 localStorage 需要设预算（超预算从栈底淘汰并**在日志里明说"最早 N 条不再可跨刷新撤销"**，不静默丢）。`clearUndoStack` 必须同时清持久化副本 —— 导入备份 / `resetToSeedData` 都会整库重建、id 全部重排，留着的旧栈会去改重排后的记录。

顺带修一处同源缺陷：`performUndo` 现在对每个子步骤 `catch { console.warn }`，失败被吞掉后仍返回 `{ok:true, reverted:N}` —— 部分失败在界面上完全看不见。改为返回 `{ok, reverted, failed:[{why}]}` 并由卡片如实显示。

**P2-2 操作日志补全** —— 落点 `stores/partsDomain.js`、`stores/appStore.js`、`stores/nlActions.js`

**关键设计：低层"改字段"入口默认不记日志**（`updateEquipment` / `updateWorkOrder` 要显式传 `{log:true}` 才记）。理由不是洁癖 —— 撤销的**两条路**（闭包与可序列化描述）最终都调这两个函数，默认记日志会把"撤销"记成"用户编辑了一次设备/工单"，而撤销恰恰是最不该伪造操作记录的动作。这个不变量由断言锁住，并且断言**同时要求"撤销确实改动了数据"**：少了这一半，撤销整个失效时"日志里没有编辑记录"会静默变绿（什么都没做，自然什么都没记）。

**顺带修掉一处审计链自相矛盾**：`recheckFailedAndReopen` 先调 `markRecheckDone` 再重开单，于是日志页上是"复诊完成：X「Y」"紧跟"复诊未通过：X「Y」"——同一件事读出两个相反结论，而结论只有一个（复诊做了，没通过）。改为 `markRecheckDone(id, {log:false})`，结论由"复诊未通过"那条统一写。

**故意不做**（各有理由，留着比补上更对）：
- `resetToSeedData` / `reloadFromDb`：整库重建，日志本来就会被 `SEED_LOGS` 整体替换，逐条补记没有意义。
- `setAlertDispositions` / `clearAlertDispositions`：与撤销是同一个"低层原语与撤销共路"问题，且 `generateOrder` 那条建单日志已经把动作写明了。
- 支撑性写入（故障案例卡 / 健康快照 / `revert*`）：不是用户动作，是别的动作的派生物。
- `addMaintenanceRecord` 的主记录日志下沉：`Equipment.vue:726` 那条"记录维保"的文案被 `scripts/e2e.mjs:1153` 断言依赖，且它记的是"病历 + 备件扣减"的汇总，下沉容易变成两条。

**被测出来的真缺陷（这次变异验证反过来抓到了我自己刚写的实现）**：`silent` 是 `addLog` 的**第二参数**，我把它写进了日志对象里（7 处）。它**不报错**：日志照写、界面照显示、断言全绿，只是 silent 静默失效 —— 每次写日志都各自 `persistAll` 一次（整库 10 张表 DELETE + 全量重写两遍），"由入口末尾统一落盘一次"这条纪律根本没生效，内存里的日志对象还多带一个野键。
能发现它，是因为 M7 变异（把 `restockPart` 末尾的 `persistAll()` 拿掉）**没能**让"silent 日志真的落库"变红 —— 日志那一侧偷偷自己落了一次盘，正好把缺陷掩盖过去：**两个缺陷互相抵消，断言看着没问题**。修完 silent 之后 M7 立即变红。已补一条断言直接盯住那个野键（见下），并用 M8 把原缺陷放回去验过一次。

**P2-5 落地（2026-09-27）** —— `scripts/bench-scale.mjs` + `npm run bench:scale`

按上一条执行，做法与 `store-check.mjs` 同源（镜像 `utils/` + `stores/` 成 ESM，Node 里真正装配 pinia + sql.js），灌数走**真实写入路径**（`addEquipment(silent)` / `addMaintenanceRecord(silent)`），不是造一个假的压测模型。实测六件事：首启 / 批量灌数 / 落盘（一次真实用户写入含整库重写 + `db.persist(force)` 序列化）/ 满库首启 / 看板 / 检索（拆成建池与打分两半）。规模参数可用 `--devices=` / `--records=` / `--manuals=` / `--chunks=` / `--repeat=` 覆盖。

**两个由它量出来、此前只能靠读代码猜的数**（2026-09-27 本机实跑，5000 台 + 5 万条 + 8 本 × 300 片，5 次取中位）：

- **维保记录的批量导入是 O(台数 × 记录数)**：1000 台时 0.054 ms/条、5000 台时 0.235 ms/条（台数 ×5 → 单条成本 ×4.4）。根因是 `addMaintenanceRecord` 每条都要 `equipmentList.find(...)` 定位设备，而 `importFromExcel` 正是逐行调它。**这给了 P2-4 一个可选的顺带项**：把设备索引改成 Map 即可从 O(台数) 降到 O(1)，但演示规模（60 台）无感、5 万行导入仍要 12 秒，是否值得动属于取舍（未做）。
- **检索的 20 ms 里九成在打分、不在建池**：池 2430 条时建池 2.2 ms、打分 20.3 ms；台数从 1000 加到 5000 两条都不变（池子大小由手册语料决定）。**这直接改了 P2-3 的着力点** —— 原计划写的是"切片池按内容分缓存"（省那 2 ms），实测下来真正贵的是 `searchKnowledge` 的逐条打分（省这部分才有意义）。P2-3 的改法按实测重排：先做打分侧，池缓存是次要的。

**一处测量陷阱**（脚本第一版就踩了，已写进脚本注释与 `docs/测试报告.md` §六）：让 `answerItems` 失效最初写的是"改一下知识条目的 `title`"，量出来 **0.0 ms**，看着像"建池不要钱"，结论正好反了 —— Vue 的 computed 只追踪它读过的东西，而 `answerItems` 只迭代了 `knowledgeItems` 数组、从没读过条目属性，所以那次"失效"根本没发生。真正能失效它的是文档那一侧。脚本里现在有一条**测量前提检查**盯着它（碰完还是同一个数组引用就打印警告）。

**P2-6 打包依赖闭包**（插入项，2026-09-25 用户装机报障）—— 落点 `package.json`、`electron-builder.offline.json`、`electron-builder.online.json`、新建 `scripts/pack-check.mjs`

用户装上的安装包里"本地模型档位下载完成但切换失败"：

```
Cannot find package 'chalk' imported from
  D:\测试\kuangshan-zhigong\resources\app.asar\node_modules\node-llama-cpp\dist\bindings\Llama.js
```

根因是 v2 白名单模型（`!node_modules/**` 打头再显式放行三个包）：**手写的白名单只能列出"我要哪个包"，列不出"我要的包依赖谁"**。node-llama-cpp 靠三条规则被重新包含了，它的 **28 个运行时依赖全被排掉**（`chalk`/`ora`/`yargs`/`fs-extra`/`ipull`/`@huggingface/jinja`…）。这类缺陷的标志是**开发态永远看不见**：`npm run electron:dev` 有完整 `node_modules`，一切正常；`vite build` 全绿、`verify` 全绿、自检全绿；只有装到机器上才炸。

改法：删掉整片排除与三条显式放行，`files` 只列 `src/main`、`src/preload`、`dist`、`package.json`；随包内容 = `package.json` 里 `dependencies` 的**真实运行时闭包**。同时把 13 个渲染侧库（element-plus/echarts/vue/vue-router/pinia/sql.js/xlsx/mammoth/pdfjs-dist/gsap/driver.js/vue-echarts/@element-plus/icons-vue）从 `dependencies` 移进 `devDependencies` —— 它们已由 Vite 打进 `dist/`，留在 `dependencies` 会被整包复制进 asar。**体积不变量因此换了守法的对象**：从"白名单条目要少"变成"`dependencies` 要保持极简"（`self-check.mjs` M 段那条断言跟着改判据）。

`scripts/pack-check.mjs` 是这一项的门禁（已接进 `verify` 链），三条判据：① `src/main`/`src/preload` 里 `require`/`import` 的裸包名必须是运行时依赖，落在 `devDependencies` 等于打包版必崩（electron-builder 从不复制 devDependencies）；② 运行时闭包不被 `files` 规则排除 —— 它按真实 `node_modules` 自己算闭包，不靠人维护清单；③ 带 `*.node` 的包必须整包进 `asarUnpack`。

**体积与原生后端口径**：`@node-llama-cpp/{win-arm64,win-x64-cuda,win-x64-cuda-ext}` 共 542 MB，目标平台是 Windows x64，明确排除（CUDA 两个包比整个离线安装包还大）。`win-x64` 与 `win-x64-vulkan` **必须随包**，且 vulkan 不是冗余 —— 实测 vulkan 中位 450 ms、退回 CPU 14580 ms（慢 32 倍），且 CPU 那条把提示词复读三遍不作答。这条实测结论现在钉在 `pack-check.mjs` 的 `REQUIRED_BACKENDS` 注释里（原先在 `self-check.mjs` M 段）。

**P2-7 设备台账虚拟滚动**（插入项，2026-09-25 同一轮报障）—— 落点 `src/renderer/src/utils/virtualGrid.js`、`views/Equipment.vue`、`scripts/e2e.mjs`

用户报"设备台账界面无法显示全部设备"。实测：容器高 **4736 px**（60 台设备全展开的高度），只渲染了 **12 张**卡片，滚动条拖到底也还是那 12 张。三个原因叠在一起，缺一个都不会出错：

1. 虚拟滚动的占位 spacer 用 `padding-top/padding-bottom` 撑，而占位元素与滚动容器是**同一个** `div`。全局 `box-sizing: border-box` 之下，padding 大于 `max-height` 时内容盒被压成 0，元素的**实际高度就等于 padding** —— `max-height` 彻底失效，容器被撑成 4736 px。
2. 量视口高用 `ResizeObserver.contentRect.height`。它**不含 padding**，于是容器量出来是 0，可见行数算成 0/负数，渲染窗口永远停在首屏。
3. 行高/列数按 CSS 里的估值写死（`cardHeight: 280`、`cardMinWidth: 300`），CSS 一改占位就错位。

改法：占位挪到**内层 flex 包装元素**（滚动容器与占位载体必须是两个元素）；量视口改 `entry.target.clientHeight` 并加 `> 0` 守卫；给了 `itemSelector` 就按**真实 DOM** 量行高与每行列数（同一 `top` 的卡片刻数），CSS 漂移也不会错位。同时把 `containerProps` 那个"零消费方"的 v-bind API 换成 `bind(el)`。

**e2e 那条断言原先把这个缺陷**当成了正常现象：`cards >= 1 && cards <= 60` 配一句"首屏约 12 张"的注释 —— 断言能从 1 到 60 全绿。改成三条：滚动能摸到的**去重设备名必须是 60 台**（扫描按一个视口一步走，**不能**直接跳 `scrollHeight`，那样只看到首屏和末屏，实测会漏报成 36/60）、容器高必须被夹在 `> 200` 且 `<` 视口高之间、末张卡片必须进视口。放回缺陷时实测红：`可达 18/60 台`。

**P2-8 下载模型删除 / 拔插**（插入项，2026-09-26 用户报障）—— 落点 `src/main/llmEngine.js`、`src/main/modelManager.js`、`src/main/ModelRegistry.js`、`src/main/index.js`、`src/preload/index.js`、`src/renderer/src/utils/modelsClient.js`、`views/ModelHub.vue`、`scripts/main-check.mjs`

用户报"本地模型下载后无法删除，无法正常拔插"，并给出精确报错：

```
删除失败：EPERM, Permission denied: \\?\C:\Users\kong\AppData\Roaming\kuangshan-zhigong\models\standard
```

**这不是"文件被占用"那类偶发问题，是必然失败** —— 五个原因叠在一起，缺一个都不会是这个现象：

1. **删除从不释放会话。** llama.cpp 是在**进程内 mmap** GGUF 的，映射还活着时对文件 `fs.rmSync` 必然 `EPERM`。实测：加载 standard 后直接删目录 = 用户看到的那行报错逐字一致；先 `session.dispose()` 再删 = 立刻成功。`deleteModel` 原先一行释放逻辑都没有。
2. **两份 `modelRoots()` 各写各的。** `llmEngine` 用 `app.isPackaged ? process.resourcesPath : join(__dirname,'../../resources')`，`modelManager` 用 `process.resourcesPath || ''`（开发态指向 Electron 自带的 resources，裸 node 下退化成**相对路径** `'models'`）。同一个概念两份实现 → 统一到 `modelManager` 那份（`bundledModelsDir()` 感知 `isPackaged`），`llmEngine` 改为 require 它。
3. **`scanTiers` 在第一个命中的根目录处短路。** 于是"哪份被加载"和"哪份可删"被混成一件事：随包副本与下载副本同时存在时，短路拿到的是先出现的那份。新增**非短路**的 `locateTier(tier, dirs)`（逐根目录各报一份），`installDetailFor` 据此分别告诉界面"随包的在哪、下载的在哪、能不能删"。
4. **删除按钮对"随包只读"和"正在使用"的档位照给**，且没有可删内容时 `deleteModel` 返回 `{ok:true, deleted:false}` —— 界面只看 `ok`，于是如实弹出"已删除"，而那 1.04 GB 原地没动。
5. **`autoSelectTier` 在空集上无条件返回 `'light'`。** 删掉当前档位后要重新指向，直接采信它就会指到一个**并不存在**的档位上（所以重选时必须显式加空集守卫）。

改法：`deleteModel` 转异步并接收释放钩子，`release` 在 `rmSync` **之前**调用；逐目录删除带重试（`EBUSY/EPERM/EACCES/ENOTEMPTY`，4 次 × 250 ms —— 卸载后句柄不是立刻关掉的）；成功回报真实释放体积与被删路径；失败给可照做的文案（"先停用本地模型或关闭 AI 助手后重试；若仍失败，可手动删除 `<下载目录>` 下的「`<档位 id>`」目录"）；连旧版目录名（`qwen2.5-0.5b/`）一起清，避免"已删除但还装着"的假象。`llmEngine` 侧新增 `releaseTierForRemoval(id, {willRemain})`：释放会话 →（若该档位彻底消失）从**过滤掉被删档位之后的真实已安装集合**里重选，空集显式置 `null` 并持久化偏好。

**两处设计由用户裁决**：① 模型存放位置**保持现状**（下载副本留在用户数据目录，不搬进安装目录），界面把真实路径写出来并提供「打开目录」；② 删除**当前正在使用**的档位**允许**，删完自动切到另一个已安装档位。

### 第四批 · 应用锁与身份（2026-09-27 用户定稿）

**背景**：路演现场笔记本要转给评委上手，需要一把锁把界面挡住；同时用户要求"界面显示谁在用、什么身份"。于是这一批**不做纯锁**，做成"轻量身份 + 界面锁"。

**已裁决的四件事**（2026-09-27 用户逐条选定，不再改）：

1. **深度 = 界面锁，不加密库文件**。`userData/*.db` 仍可被任何工具直接打开 —— 这条必须写进 README「已知边界」，不许含糊（演示开场讲的是"设备参数、故障记录是商业机密"，被评委追问时口径必须一致：锁的是**界面**，不是**文件**）。
2. **时机 = 启动时锁 + 空闲自动锁**（默认 10 分钟，设置页可开关/调时长）。**不做**手动锁定按钮（用户未勾选；后续想加是一行按钮的事）。
3. **凭证 = 多账户，姓名 + 4~6 位数字 PIN**。角色**只做标识**：界面显示 + 进操作日志；**不做**权限拦截（明确列为后续项，不许默不作声地假装有权限）。
4. **忘记凭证 = 锁屏页提供「清空本机数据并解锁」**，二次确认且如实写明后果（台账/工单/手册/日志全部清空、重新播种演示数据）。

**三条铁律自检**：PIN 校验用 WebCrypto 的 PBKDF2，全程本机、零联网 ✓；账户只落本机 localStorage、不上传 ✓；不触碰数字不变量 ✓。

**P4-1 应用锁与账户存储** —— 落点 `utils/appLock.js`（新建）、`components/LockScreen.vue`（新建）、`App.vue`、`utils/database.js`（**只增**）

- 账户形状：`{ name, role, salt, hash, iterations, createdAt }`，存**本机 localStorage**（`ks:app-lock`）。
  **为什么不进数据库**：锁屏必须**先于数据库打开**就生效 —— 判断"锁没锁、PIN 对不对"这件事发生在开库之前，把凭证放库里等于自相矛盾。浏览器与 Electron 渲染进程都有 localStorage（撤销栈 `ks:undo-stack` 已经在用）。
- PIN 不存明文：PBKDF2（`crypto.subtle.deriveBits`，SHA-256）+ 每账户随机盐 + 迭代次数一并记录，离线可用、无任何外部依赖。
- **如实说明（写进源码注释与 README）**：锁配置在 localStorage 里，**清掉它就绕过了锁**；账户列表本身也是明文（姓名/角色不加密）。**这是防"旁人随手翻看/误操作"的锁，不是防技术人员的锁。**
- **启动时序**（本项最大的风险点）：`App.vue` 必须在 `initStore()` **之前**判锁；未解锁时只渲染锁屏，业务数据**不渲染也不装载**（Electron 下不许闪一下数据再盖住）。
- 验收：self-check 一组纯函数断言（同 PIN 同盐可验证通过、错 PIN 拒绝、不同盐 ⇒ 同 PIN 不同哈希、PIN 长度 4~6 位校验、清空自救清的键集合正确）；e2e 断言"启用锁后刷新 ⇒ 出现锁屏**且台账数据不在 DOM 里**"。这条必须能失败：把判锁挪到 `initStore()` 之后，断言必须变红。
- 与 e2e 的关系（**必须显式处理**）：e2e 每次运行都会清空本机数据，而**锁默认不启用**（没有账户 = 不锁），所以默认不受影响；一旦启用，e2e/探针通过 CDP 预置 localStorage 键来进入"已登录"状态 —— 这是**测试预置状态**，不是给产品加后门。

**P4-1 落地（2026-09-27）** —— 落点 `utils/appLock.js`（新建，335 行）、`components/LockScreen.vue`（新建）、`main.js`、`views/Settings.vue`、`utils/backup.js`（注释）

**三处实现取舍**（都写进了源码注释，不是事后解释）：

- **锁屏是一个独立的 Vue 应用**，不是 `App.vue` 里的 `v-if` 分支。原计划落点是 `App.vue`，实施时改掉了：`App.vue` 里判锁意味着**数据库已经装载完、路由已经建好、只是渲染时被挡住** —— "不闪数据"就变成一句要靠人记得写对的约定。改成独立应用后，未解锁时主应用**根本没有被创建**，`initStore()` / 模型预热 / 引导演示一概没有机会启动，这条从"约定"变成**结构保证**。代价如实列出：锁屏拿不到主应用的全局组件与错误边界，所以它只用 `BrandMark` + `el-input`，出错走控制台（装边界会与主应用重复监听 window `error`，一次异常记两条日志）。
- **换挂是"先装载、后换挂"**：`handleUnlock()` 里先把主应用装好再去 `lockApp.unmount()` → `app.mount('#app')`。冷启动播种要几秒，这段期间锁屏还留在屏幕上、按钮显示「正在校验…」，比给一块白屏好。两步都是同步的，中间不会真的空一帧。
- **解锁状态只放内存**（模块级 `unlockedAccountId`），刷新/重启必回锁定态 —— 这正是"启动时锁"的实现方式；落盘的话就变成"锁一次管一辈子"了。

**三条如实声明**（与 README「已知边界」同口径，源码注释、设置页卡片、README 三处一致）：① 锁的是**界面**不是**文件**，`userData/*.db` 仍可被任何 SQLite 工具直接打开；② 锁配置在 localStorage（`ks:app-lock`），**清掉它就绕过了锁**，账户列表本身也是明文（姓名/角色不加密）—— 这是防"旁人随手翻看/误操作"的锁，不是防技术人员的锁；③ 角色**只做标识**（界面显示 + 进操作日志），不做任何权限拦截。

**为什么凭证不进数据库**：锁屏必须**先于数据库打开**就生效 —— "锁没锁、PIN 对不对"这件事发生在开库之前，把凭证放进库里等于自相矛盾（要么先开库才能判锁，要么判锁时还没有库）。这也是把 P4-3 的"界面显示当前身份"提前下沉到 P4-1 设置页卡片（`.lock-current`）的原因：锁一启用，界面上就得能看出"本次以谁的身份进入"。

**`ks:app-lock` 刻意不进备份白名单**（`utils/backup.js` 注释）：导出的备份里带上账户 PIN 摘要，只会让"备份文件"变成一份可离线爆破的凭证。导入侧本就按白名单逐键写回、不清别的键，所以**换机导入备份后目标机器的锁保持原样**。「重置演示数据」（`appStore.js` 的 `destroyDatabase({clearStorage:true})`）同理不碰锁配置 —— 重置数据不该把锁一起废掉；只有锁屏上的「清空本机数据并解锁」会清它（`RESCUE_KEYS`），而且只清被这次清空真正作废的三个键（`ks:app-lock` / `ks:undo-stack` / `ai_chat_messages`），**不动**主题、导航钉住、老师傅模式这些偏好。

**落地（已完成）**

计划里写的是"`visibilitychange` 重置计时"与"e2e 把阈值调到 1 秒"，两处都按实现改了，理由如下：

- **`visibilitychange` 刻意不算活动**。人离开时把窗口最小化、三小时后回来 —— 那种情况恰恰应该锁；把"窗口重新可见"当活动就等于"离开再回来永远不锁"。回来后第一次按键或点击自然会重置计时。
- **最短档是 1 分钟，不是 1 秒**。阈值单位是分钟（`idleMinutes` 只接受 0 或 1~240 的整数，非法值报错不静默收敛），所以 e2e 用的是**设置页能选的最小档**；想要更快只能绕开界面直接写 localStorage，那测的就不是用户走得通的那条路。

**到点做什么：`lockNow()` + `location.reload()`，不是就地盖一层遮罩。** 就地盖一层看着更"优雅"，但那样 store、路由、模型全都还活着、只是被挡住 —— 那正是 P4-1 特意避开的"靠约定"。重载会重新走一遍启动判锁，于是"未解锁时业务数据不装载"这条**结构保证在自动锁之后同样成立**。代价如实说明：锁的那一瞬会闪一下重载。这是本项目"能失败验证"最想要的一条 —— 把 `location.reload()` 去掉，e2e 立刻会红（见下表 M8 同族的判据）。

**计时器只在启动装载时安装一次**（`installIdleLock` 在 `bootAppData` 末尾）。于是在"本次运行里刚启用应用锁"这一种情况下，要到下次启动才有计时器 —— 这与整个应用锁"锁在下次启动才生效"的口径一致，设置页卡片上把这件事写明了。计时器每 15 秒醒一次，**每次都重读阈值**，所以改档位当次生效、不用重启。

**先落盘再上锁**：`store.saveNow()` 之后再 `lockNow()`，因为重载会丢掉未落盘的变更；落盘失败也照样锁（锁失效比丢一次自动保存严重得多），只记一行控制台。

**`disableLock()` 保留空闲设置**：停用再启用（换个账户、临时关一下）是常见操作，顺手把用户选的档位抹回默认 10 分钟是另一件事。

**断言**：self-check 376 → **393**（新增 17 条：默认 10 分钟；恰好到阈值锁 / 差 1 毫秒不锁 / 远超阈值锁；阈值 0 不锁；`undefined` / `NaN` 阈值当关闭；时钟回拨不锁；时间戳 NaN/Infinity 不锁不抛；1 分钟档按 1 分钟算；设 0 能存住；设 30 能读回；非法值 2.5 / -1 / 1e9 / 'abc' 一律拒绝**且不改动已存值**；落盘是 number 不是 string；脏值回落 10；加账户不抹空闲设置；`lockNow` 只清会话（账户还在、锁仍启用）；`disableLock` 保留空闲设置）；e2e 181 → **190**（新增 9 条，跑近三分钟）。

- **摘列是取舍，逐页写明"让谁、为什么"**（注释留在各自视图里，self-check ④ 盯着不让它悄悄消失）：规程库摘「分类」「来源」——"来源"是可追溯信息，但详情抽屉里一字不差地还在；"关键词"留着，它是现场判断"这条跟我这台机器对不对得上"最直接的线索。复诊管理摘「复诊日期」而**必须留下「是否到期」**（那才是这页的重点，原先它正好被右侧固定列盖住）。手册资料库摘「大小」「添加时间」。工单 / 备件两张表早先就接了 `isNarrow`，**此前一条断言都没有**，本项顺带补上 —— "写好了没人验"与"没写"在验收上是同一件事。
- **实测（2026-09-27，CDP 量 `body-wrapper .el-scrollbar__wrap` 的 `scrollWidth - clientWidth`）**：**900 / 1100 / 1366 / 1440 四个宽度下，上述页面全部 0 溢出**。1366 这一档是刻意加的 —— 它刚好卡在断点之上，属于"并排但很挤"的边界；病历表备注列的 `min-width` 由 160 收到 140 就是为了它（差这 20px 就从"表格自己滚动"变成"放得下"）。
- **断言**：e2e 204 → **217**（新增 13 条，全在 13b 段：1440 对照 2 条 + 四页摘列/不溢出 8 条 + 病历折行/五列 2 条 + 收尾视口还原 1 条）；self-check 407 → **413**（新增 6 条 T 段：断点严格小于门禁视口、探测器自证、"v-if 与 `useNarrowMode()` 两半都得在"、接线名单、病历卡基准宽 ≥ 表自然宽、让位注释留痕）；其余门禁不变。
- **1440 那一条对照是后补的，补的原因值得记**：Mn3 把病历卡基准宽打回 300px 时，1100 那两条如实见红，而 **1440 这一档一条断言都没有、纹丝不动** —— 也就是说那个 180px 的缺陷"放回去"仍然全绿，修过归修过，**没有断言守着它**。补上后 Mn3 复跑，这一条如期变红（README 与此处都以断言为准，不以"我看见修好了"为准）。
- **能失败验证：e2e 5 次变异 + self-check 6 次变异，各自精确见红**（详见下表）。两处**如实说明**：
  1. **Mn4 只红了规程库一处**（原本预期会红更多）：其余页面都是"改窄之后才导航过去"的，组件挂载时读到的就已经是窄屏，**根本不需要 resize 事件**；只有规程库是先按 1440 加载、再改窄。也就是说"resize 监听那条路"**只有那一条断言真的在验**。
  2. **900px 以下没有逐页走查**（本次量到 900 为止）：更窄的窗口下折行成单栏之后可能还有别的挤压，**未验** —— 这是不覆盖，不是"已覆盖"。
