## 二、各套件覆盖内容

### 1. 静态检查 `npm run lint`

刻意只启用 `eslint-plugin-vue` 的 **`flat/essential`**（只含"会导致运行时报错"的规则），而不用 `recommended` —— 后者一半是排版规则，接入当天会刷出上千条格式告警，真正的 bug 会被淹没。风格问题交给人工评审。

在此之上显式启用了本项目吃过大亏的规则：

| 规则 | 为什么必须开 |
|------|-------------|
| `vue/no-undef-properties` | 模板里调用未导入的函数会导致**整页白屏**，而自检和端到端都可能漏掉 |
| `vue/no-unused-components` | 模板 import 了却没用的组件 |
| `vue/no-side-effects-in-computed-properties` / `vue/no-mutating-props` | 状态污染类问题 |

**规则有效性验证**：`vue/no-undef-properties` 已用故意注入的未定义绑定验证过确实会报错，而不是静默失效：

```
src/renderer/src/views/Equipment.vue
  2:45  error  'equipmentPhoto_not_defined' is not defined  vue/no-undef-properties
```

### 3. 指代消解覆盖矩阵 `npm run coverage`

> **这不是代码覆盖率**，而是口述指代的**能力广度矩阵**：对 60 台演示台账构造四类说法，统计消解结果。

| 说法类型 | 示例 | 命中率 |
|---------|------|--------|
| 类别 + 序号 | 「3 号挖掘机水温高了」 | **12/12 = 100%** |
| 全名 | 「卡特彼勒 320D 挖掘机-01」 | **5/5 = 100%** |
| 仅型号 | 「XE215C水温高了」 | 17%（5 句唯一命中，24 句返回多台候选，**预期回问**） |
| 仅类别 | 「装载机坏了」 | 0%（10 句全部返回候选，**预期回问**） |
| | **总命中率** | **22/56 = 39%**（仅供参考，句数随车队覆盖变化） |

四类说法中，「仅型号/仅类别」本就不该猜 —— 现场口语说"装载机坏了"时，工程师自己知道是哪台，系统必须问。**回问是预期行为，不是缺陷**。底线断言把这一点固化下来：

- ✅ 类别+序号、全名保持 100%
- ✅ 仅型号/仅类别**不出现"未找到"**（能列候选，而不是查无此设备）
- ✅ **唯一命中总台数 ≥ 22**（绝对台数基线，不随车队扩编稀释）
- ✅ "仅类别"**全部回问**（10/10，多台同类时绝不猜一台）
- ✅ 完全找不到的句子为空

> 关于第 3 条为什么用绝对台数而不是命中率：这个比例的分母是语料句数，而句数会随车队覆盖的型号与类别数量一起增长。2026-09-13 扩充机型库（挖掘机 5→7 个型号，新增叉车/起重机两个类别）后，句数 41→56、唯一命中 17→22（**能力其实上升了**），比例却从 41% 掉到 39%。用比例当底线，等于把"车队覆盖更全"误判成"解析能力退化"。

### 5. 端到端 口述录入 `npm run e2e:nl`（28 条）

单独覆盖"说一句话"这条链路的**每一个安全边界**：

```
说一句话 → 理解卡（不写库） → 歧义必须问 → 确认 → 真落库
        → 刷新仍在 → 撤销 → 纯查询不误写
```

关键断言：

- 解析阶段**不产生任何写入**（必须确认后才落库）
- 存在未确认歧义时**禁止一键写入**
- 设备歧义时给出候选列表且确认按钮禁用
- 点选候选后解除阻塞且可确认
- 纯查询不产生写入、不出现写入理解卡
- 撤销后工单数减少 1 且撤销栈清空该项
- 完成工单时自动生成复诊任务（闭环）

其中 #1、#11 属于同一类：**模板里引用了不存在的东西 → 整页白屏，而当时的自检全绿**。这正是本项目把 `vue/no-undef-properties` 列为必开规则的原因。

#13 是另一种"行为测试抓不到"的缺陷：加了列却没接线，同一个会话内一切正常，只有重启才暴露。因此自检里补了一条**源码结构校验**：`work_orders` / `equipment` / `maintenance_records` 等表的每一列，都必须出现在对应的写库映射函数里。

#17 是最隐蔽的一类：`push` 进数组的普通对象，事后改它的字段不触发任何重渲染。它此前之所以看着正常，是因为模板整个写在一个大组件里，任何别的响应式变化都会让该组件整体重渲染、顺手把最新值重读一遍——**缺陷被架构的粗粒度掩盖了**。拆出子组件后 props 引用不变、子组件不重渲染，问题立刻显形。这类"拆开才暴露"的缺陷，是拆分本身最大的副产品价值。

#19 值得单独记一笔：它出在**守卫自己**身上。扫描器正则写错 → 一条违规都没扫到 → 断言以"全绿"通过。为了不再犯，凡是靠扫描实现的守卫，都先断言"它认得出一段已知的违规写法"，再断言"仓库里没有违规"——**先证明它会响，再相信它没响**。

#14 则暴露了端到端脚本自身的一个盲区：原先"刷新后数据不丢"用的是 `Page.navigate` 到**同一个含 hash 的 URL**，属于同文档导航，压根没重新加载 —— 断言一直是"通过"的，但它验证的东西比名字承诺的少。改用 `Page.reload` 后才真正覆盖。

### #20 #21：自动化验收**结构上抓不到**的一类

上面 19 条几乎都来自自检或端到端，但 #20 与 #21 **不是** —— 两套端到端脚本全绿的情况下，它们依然存在。原因不是脚本写得不够，而是这类缺陷的性质：

- #20 是**对比度**问题：文字和底色的色值各自都是对的，`getComputedStyle` 查出来也"有颜色"。只有把照片和那层半透明药丸一起渲染出来，人眼才知道读不出来。
- #21 是**布局遮挡**问题：DOM 里「复诊」列的元素**存在、可见、文本正确**，任何"元素是否存在/文案是否正确"的断言都会通过。它是被右侧固定列**画在上面**盖住的 —— 这是渲染层的事。

端到端脚本断言的是"数据和交互对不对"，这两条属于"画出来能不能看"。**自动化验收对视觉缺陷是结构性失明的**，所以本次 UI 打磨是靠无头浏览器批量截图后逐张看图抓出来的，不是靠断言抓出来的。

> 结论写在这里以免误读：`npm run verify` 全绿**不等于**界面没问题。视觉这一层目前靠人工过截图，尚未做成自动化（无头截图比对基线是一条可行的路，但阈值调校成本高，本轮未做）。改完界面的自查清单见 [`视觉规范.md`](视觉规范.md) 第五章。

### #22 附：`win-x64-vulkan` **不能**排掉 —— 源码推理与实测相反

打包瘦身时最像"明显冗余"的一项是 `@node-llama-cpp/win-x64-vulkan`（约 99 MB）。读源码确实支持这个判断：

```
getGpuTypesToUseForOption() → [cuda?, vulkan?, false]     // false = CPU，永远是最后一项
getLlama() 按顺序 try/catch，只在最后一项上 rethrow
```

CPU 兜底路径真实存在，排掉 vulkan 程序也不会崩。**于是实测了一次，结论反了** —— 把 `node_modules/@node-llama-cpp/win-x64-vulkan` 临时移走再跑同一段生成：

| 后端 | 生成 128 token 耗时（三次取中位数） | 输出 |
|------|--------------------------------------|------|
| vulkan（本机实际选中） | **450 ms**（438 / 450 / 571） | 正常作答 |
| 退回 CPU（`llama.gpu === false`） | **14580 ms**（10618 / 14580 / 37988） | **退化**：把提示词原样复读了三遍，没有作答 |

慢 **32 倍**，而且不只是慢 —— 演示时那句话会变成一段复读机。移除后 node-llama-cpp 如实打印了 `A prebuilt binary was not found, falling back to using no GPU`，说明兜底确实生效、不会崩；**"能兜底"和"兜底要付多少代价"是两件事**，只看源码会得到一个能让演示现场卡住的"优化"。

所以这 99 MB 保留，并且在 `npm run self-check` 里加了一条断言把它钉住：任何人再"顺手排掉 vulkan"，自检会红，并直接打印出这个 32 倍的实测结论。

> 顺带确认了一件没做的事：`node_modules/@node-llama-cpp/win-x64-cuda`（168 MB）与 `win-x64-cuda-ext`（351 MB）合计 519 MB，白名单把它们排掉了。本机实测两个后端都选中的是 vulkan，说明这台机器走不了 CUDA；为一个 0.5B 模型多背 519 MB 不划算，未纳入。

### #22 附二：体积降了，不等于还能跑

`files` 从"排除清单"改成"白名单"后 asar 掉到 15.1 MiB（-93%），但**光看体积不足以证明还能跑** —— asar 里少一个包，症状是装到评委机器上点"加载模型"才炸，而 `vite build`、`verify`、自检全都不会响。

所以本轮另外做了一次打包产物的**运行期**验证（`win-unpacked`，不是浏览器模式）：

1. 启动 `release/win-unpacked/矿山智工.exe`，确认窗口渲染、preload 白名单注入（`window.electronAPI.llm` 在）；
2. 走真实路由进「本地模型」页（页面挂载时会自动触发加载），轮询**主进程状态机**直到 `ready` —— 模型加载 4572 ms；
3. 再**真的生成一次**（278 ms），输出《徐工 XE210C 挖掘机的健康分是62，主要扣分项是维保超期18天。》；
4. 断言主进程日志里没有 `MODULE_NOT_FOUND` / `ERR_DLOPEN`。

文件清单只能证明"东西还在"，第 2–3 步才证明"留下的那些**能被解析、能被 require、能真的跑出一段话**"。

> 这里也踩了一次"断言选错对象"：探针最初判断就绪靠的是**页面文案**里出现"就绪"二字且没有"加载中"，结果页面静态文案本来就含"就绪"，探针立刻假通过、当场放行，而真实状态是 `loading`。改成只认主进程返回的 `state` 字段才可靠。**文案会改、会重复出现在别处；状态机不会。**（与 #19「先证明它会响」同源。）

### #23 附：守卫的第一版，断错了不变量

#19 记的是"扫描器正则写错，扫不出东西却全绿"。这次是同一族的另一种形态：新写的打包守卫第一条断言是

```js
files[0] === '!node_modules/**'     // ← 错的
```

它第一次运行就 FAIL（实际首位是 `src/main/**/*`）。**失败的不是仓库，是这个断言**：白名单能成立靠的是"排除项排在放行项之前"，而 `src/main`、`dist` 那几条与 `node_modules` 不重叠，排在前面完全无害。真正的不变量是顺序关系，不是绝对下标。

改对了之后，又补了一次**反向验证**：临时把排除项挪到数组末尾、重跑自检，确认它真的会 FAIL，再还原。

> 这两条合起来的教训：断言写得越像"把当前状态抄一遍"（`files[0]` 就是现在的样子），越容易在实现一变就报假警，或者在坏掉时恰好还成立。写守卫时该问的是"**什么条件下它会红**"，并且真的去造那个条件试一次。

### #24 附：三本随包手册的正文都是**英文原版**

手册检索这一项最初是按"打分依据选错了"来修的：手册切片的元数据整本相同（同一个 title/model），所以同一本手册的每页必然同分，排序退化成插入顺序，恒引用第 1/2/3 页。改了打分依据之后，页码**还是**不对 —— 于是去量了一下手册正文本身：

| 随包手册 | 汉字数 | 字母数 | 结论 |
|---|---|---|---|
| SQ10SK3Q 随车起重机 操作维护手册 | 483 | 31835 | 英文为主 |
| QY25K5D 汽车起重机 技术规格书 | 2001 | 7476 | 英文为主 |
| XCA60E 全地面起重机 技术规格书 | 2324 | 9464 | 英文为主 |

旗舰那本操作维护手册里，**「液压」「钢丝绳」「保养」「润滑」「检查」一个都搜不到**（汉字 483 个基本只是页眉的公司名）。中文提问与页面文字没有任何公共子串 —— 这跟打分权重完全无关，再怎么调参也命中不了。检索到的"第 N 页"只可能是插入顺序，而它在界面上和正确答案长得一模一样。

顺带发现旧断言为什么是绿的：它断言"两个不同问题必须引用不同页"。修好之前，液压问出 1/2/3、钢丝绳问出 1/4/5 —— **两个都错，却满足"不同"**。断言描述的是一种"看起来在检索"的表象。

修法：加一张 `synonyms.MANUAL_TERMS` 中文词 → 英文手册用词表（40 个词，**逐个在随包正文里查过、确实出现的才收**），并且只翻译**非身份词** —— 「起重机」译成 crane 也仍然说明不了是哪一页（crane 出现在 86 片里的 42 片），中文侧刚把它剔掉，英文侧不能再从后门放进来。另加词频倍率打破同分（「液压系统怎么保养」曾有 7 页同时命中 hydraulic + maintenance、全部同分）。

修完的实测结果（自检探针与端到端**页码一致**）：

- 液压 → 第 **30**/5/29 页（第 30 页是 `H.02 Maintenance schedule`：`Replace hydraulic oil filter… Check the rope and replace it in time. Maintenance every 900 hours`）
- 钢丝绳 → 第 **30**/33/29 页

新增的端到端断言直接问引用的正文本身：答文里嵌着切片原文，液压答文必须出现 `hydraulic`、钢丝绳答文必须出现 `rope`。**这条在修好之前是会红的**（答文引的是封面那句 `Caution: Read this manual carefully…`）。

已知不足：目录页仍会排进前三（第 5 页罗列了所有章节名，天然命中多个检索词且词频高）。这不是算分算错，首位引用已是正文页，暂不额外处理。

### #25 附：边界卡两头，把变形词全卡死了

英文词要用词边界匹配，是因为正文里的 `proper installation` 含有 `rope` —— 按子串数，第 34 页凭 `improper` 里的 rope 混进了「钢丝绳」的第二名（实测）。

但第一版两头都卡（`\bterm\b`），于是**所有变形词一起失效**：这本手册里只写 `intervals`（×8）、`lubricated/lubricating/lubrication`（×7），从不写光秃秃的 `interval` / `lubricat`。表里这两条直接变成死词，检索静默地少两路信号 —— 界面上只是"引用的页码变差了一点"，看不出任何异常。

改成**只卡前边界**（`\bterm`）：收得下变形（intervals、lubrication、checks、ropes），仍然挡得住嵌在别的词里（`proper` 里的 rope、`boiler` 里的 oil，前面都不是词边界）。

> #25 与 #19、#23 同族，都是"**验证工具本身**验证得比它的名字少"：#19 是扫描器扫不出东西，#23 是守卫断错了不变量，#25 是守卫按"每条至少命中一个"放行。三次都出在**写验证的那一方**，不是被验证的代码。因此这次新加的守卫都做了反向验证：塞一个正文里不存在的词 → 必须 FAIL；取消身份词过滤 → 必须 FAIL。两条都当场验证过会红再收工。

## 四、验收设计原则

1. **一条命令跑到底**。原本 e2e 要求"另开一个终端先跑 `npm run dev`"，导致 `npm run verify` 永远跑不到最后两步就退出 —— 一个需要人工介入的验收等于没有验收。现在脚本自带开发服务器（外部已起着就复用，跑完不动别人的进程）。
2. **断言要能抓到"静默失效"**。最危险的 bug 不是崩溃，而是"看起来正常但结果不对"（#4 #5 #6 #8）。因此对账类断言（件名 100% 可在台账查到、带配件记录费用不为 0、刷新前后一致）比功能断言更重要。
3. **不猜就是正确**。歧义场景下"返回候选并拒绝写入"是**预期通过**，不是失败。
4. **数字不变量必须校验**。本地模型生成的文本，其数字必须是规则引擎结论数字的子集，否则整段丢弃 —— 这条也在自检里作为纯函数断言覆盖。

## 六、复现步骤

```bash
npm install
npm run verify
```

`verify` 依次执行：`lint` → `self-check` → `coverage` → `build` → `e2e` → `e2e:nl`，任一步失败即以非零码退出。

前置条件：本机已安装 Chrome 或 Edge（端到端需要无头浏览器；可用 `CHROME_PATH` 指定路径）。
