## 零·二、2026-09-24 补充

### 甲、一个「自动化全绿、人一上手就废」的缺陷

装好的离线包交到人手里实测，第一条反馈就是它：**右上角「引导演示」按钮在，点开是空的、点不动。**
而当时 `npm run e2e` 里那三条引导演示断言**全部通过**。

| # | 缺陷 | 严重度 | 为何此前全绿 |
|---|------|--------|--------------|
| 29 | **引导演示下拉永远打不开**：触发器里嵌了一层 `el-tooltip`，`el-dropdown` 因此拿到的是**组件**而不是元素触发器，popper 从不定位 —— 菜单在 DOM 里存在、`getBoundingClientRect()` 恒为 `0×0`、坐标停在 `(0,0)`，所以人看到的是"按钮在、下拉空/点不动"（打包版实测：菜单 `0×0`，菜单项中心点命中到的是 `div.logo`） | 高（入口 100% 不可用，且正是讲超时兜底要用的那条） | 旧断言用的是 `element.click()` —— **合成点击绕过命中检测**：元素被盖住、尺寸为 0、甚至不可交互，`click()` 一样返回"成功"。于是"能点开"这件事从来没被真正验证过，缺陷一路活进了安装包 |
| 30 | **工具条上的暂停键在手动模式下是死的**：`togglePause()` 只翻 `paused`、从不把 `playing` 置真，而默认模式已是手动（`playing=false`），按下去什么都不会发生 | 中（按了没反应，演示现场最忌讳） | 同一颗按钮在自动模式下工作正常，而旧用例只在自动模式下点过它 |

同轮按用户口径改掉了引导演示的默认行为：两个入口（右上角下拉、首启自动播放）**默认手动推进**，
自动降级为工具条上可切的一档；全新电脑首次打开自动弹一次（`ks:tour-seen` 只播一次，看过不再打扰）。
详见 [`docs/演示脚本.md`](演示脚本.md) 与 [`docs/tasks/14-引导演示增强.md`](tasks/14-引导演示增强.md)。

**验收手段的相应升级**（针对"合成点击看不见命中失败"这一根因）：

- 引导演示那一组断言**全部换成真实鼠标事件**（CDP `Input.dispatchMouseEvent`：`mouseMoved` → `mousePressed` → `mouseReleased`），并在点击前用 `document.elementFromPoint()` 做命中检测，把"点到的是不是它自己"一并断言。协议层做不了假的就只有这一层。
- 断言从"卡片出现了"推进到**行为**：默认停在 `1 / 12` 且干等 4.5 秒不前进、点一下才到 `2 / 12`、标记落盘、重载后不再自动弹。
- 三条新行为都做了**能失败**的验证：把 `el-tooltip` 嵌回去 → 下拉断言立刻红（菜单 `0×0`）；把 `auto` 默认改回 `true` → 手动模式三条红（实测 `3 / 12 → 4 / 12`，确实在自己走）；摘掉"只播一次"的判据 → 重载后"又自动弹了"。
- 顺带修掉一处**测试自身的假绿灯**：那颗双角色按钮的断言原先只查终点状态，按钮找不到时也会"通过"；现在要求点击本身成功（`playBtn.ok`）。
- 三套自动化（`e2e` / `e2e:nl` / `contrast-audit`）都要面对同一个副作用：首启会自动弹出遮挡层，而 driver.js 的遮罩**拦鼠标**，会挡住点击与取色。共用 `scripts/devServer.mjs` 的 `seedTourSeen()` 在导航前种下"已看过"标记；验首启的那段用 `unseedTourSeen()` 先撤回注入再重载 —— 这一对函数是必需的，因为注入按**文档**生效，只 `removeItem` 再刷新的话标记会被种回来，首启路径永远测不到。

### 乙、深色对比度门禁一直在报**假红**

同一轮顺手复核 `npm run audit:contrast:dark`（它不在 `verify` 链里，只手工跑），它报 **23 类 / 第一屏 109 处不达标**：样本长这样 —— `#e8eefb`（深色令牌的正文色）压在 `#ffffff` 上 1.16:1，以及 `#0a1326`（浅色令牌的正文色）压在 `#121b30`（深色的顶栏底）上 1.08:1。同一屏上同时出现"深色字 + 浅色底"和"浅色字 + 深色底"两种反向混色，只能是一种情况：**这些颜色根本不是稳定态**。

量了一下：深色令牌块该有的都有（`--chrome-ink` / `--card-2` / `--danger-soft` 全部在 `html[data-theme="dark"]` 里重新定义过），与"漏定义令牌"无关。真正的原因是**采样拍到了过渡动画帧**：

| # | 缺陷 | 严重度 | 为何此前没被发现 |
|---|------|--------|------------------|
| 31 | **`audit:contrast:dark` 在主题过渡途中取色**：脚本每条路由采样前会把 `data-theme=dark` 兜底注入一次（因为它知道 bootstrap 会改回浅色），但**紧接着就采样**。项目里有十几处 0.15~0.3s 的 `transition: background/color`（tokens.css 统一时长段 + EP 自带），翻主题会把元素从浅色动画到深色，立刻采样等于拍动画帧 | 中（假红会腐蚀门禁：要么被人当噪音忽略、要么被逼着放宽阈值，两种都会放过真问题） | 只有**第一条**路由中招：hash 导航不重建文档，深色属性留在 `<html>` 上，之后每条路由的"兜底注入"都是空操作、没有过渡。于是 109 处假红全挤在 `/dashboard` 一屏上，看着特别像"深色主题问题很多" |

修法是翻完主题等 600ms 再采样（`scripts/contrast-audit.mjs`）。修完深色审计一次全绿 —— 也就是说**深色主题本身没有这 109 处问题**，此前那份"深色也 0 违规"的记录碰巧是对的，但它是碰运气对的：换个更慢的机器、或以后谁把过渡时长调长，它就会红。

> 教训与 #29 #30 同一条：**门禁给出的颜色 / 命中 / 时序，都得是稳定态的那一份。** 断言"元素出现了"不等于"元素能点"，断言"颜色不达标"也不等于"配色真的不达标"。

## 零·三、2026-09-27 补充（P4-3「身份进审计」一轮）

### 甲、开发服务器被 Vite HMR 污染：断言会**静默空转**

| # | 缺陷 | 严重度 | 为何此前全绿 |
|---|------|--------|--------------|
| 32 | **被改过的模块，在页面里同时活着两份实例**：Vite 会把**引用它的说明符**改写成 `utils/database.js?t=<时间戳>`，于是"应用实际跑的那份"（`initDatabase()` 也 init 在这份上）与"验收脚本按裸路径 `import()` 拿到的那份"成了两个模块 —— 后者的模块级 `db` 永远是 null | 高（能让门禁**假绿**，不只是假红） | 症状一分为二：一半是吵的（抛「数据库未初始化」，整轮 e2e 只留一句堆栈），另一半是**不吵的** —— 形如"锁屏时 `isReady` 必须是 false"的断言在双实例下**恒真**：它读到的那个实例本来就没初始化过，于是它一直在验证一个空集合。吵的那种会被反复排查，不吵的那种没人会去查 |

判据（两分钟能验）：干净服务器上 `curl -s <base>/src/stores/appStore.js | grep -c 'utils/database.js?t='` 得 **0**，被污染的得 1。

修法不是"每次跑验收前先重启开发服务器"—— 那要求每个跑验收的人**先知道这件事**，而不知道的人得到的是一份看起来全绿的报告。`scripts/devServer.mjs` 新增 `resolveCleanBase(base)`：**体检到污染就换端口自起一份干净的**（体检本身失败不拦路，宁可照旧跑也不要把验收卡死）。`e2e` / `e2e:nl` / `contrast-audit` 三个脚本各自顶层 await 调它。2026-09-27 的全量 verify 里这条守卫**真实触发过一次**：5173 被污染 → 自动改到 5174 跑完 203/203。

> 教训是 #29 #30 那条的延伸：**"断言全绿"要先确认它真的在测那件事。** 一条恒真的断言和一条通过的断言，在报告里长得一模一样。

### 乙、"没有输出"不等于"卡死"（一次误判，白丢两轮 e2e）

`scripts/e2e.mjs` 默认**逐条静默**：打完开头三行（浏览器探测、"清空本机数据"）之后直到结束都不再有输出 —— 逐条 `PASS/FAIL` 要 `E2E_TRACE=1`，默认只在末尾统一汇总。这个设计没问题，问题在**照这个过程监控会误判**：2026-09-27 我把两轮**正在正常运行**的 e2e 判成卡死、中途杀掉（当时还"有证据"：进程 CPU 停在 0.5s 不动、日志 7 分钟不变、`Page.reload` 明明有 90s 超时却不见报错）。

判断还在不在跑要看**浏览器那侧**：`curl -s http://127.0.0.1:9222/json/list` 里页面 URL 在 `#/dashboard → #/equipment → …` 之间变，就是活着。现在 e2e 起步时会自己打一行说明，省得下一个人再判一次。

### 3. 指代消解覆盖矩阵 `npm run coverage`

> **这不是代码覆盖率**，而是口述指代的**能力广度矩阵**：对 60 台演示台账构造四类说法，统计消解结果。

| 说法类型 | 示例 | 命中率 |
|---------|------|--------|
| 类别 + 序号 | 「3 号挖掘机水温高了」 | **12/12 = 100%** |
| 全名 | 「卡特彼勒 320D 挖掘机-01」 | **5/5 = 100%** |
| 仅型号 | 「XE215C水温高了」 | 17%（5 句唯一命中，24 句返回多台候选，**预期回问**） |
| 仅类别 | 「装载机坏了」 | 0%（10 句全部返回候选，**预期回问**） |
| | **总命中率** | **22/56 = 39%**（仅供参考，句数随车队覆盖变化） |

四类说法中，「仅型号/仅类别」本就不该猜 —— 现场口语说"装载机坏了"时，工程师自己知道是哪台，系统必须问。**回问是预期行为，不是缺陷**。底线断言把这一点固化下来：

- ✅ 类别+序号、全名保持 100%
- ✅ 仅型号/仅类别**不出现"未找到"**（能列候选，而不是查无此设备）
- ✅ **唯一命中总台数 ≥ 22**（绝对台数基线，不随车队扩编稀释）
- ✅ "仅类别"**全部回问**（10/10，多台同类时绝不猜一台）
- ✅ 完全找不到的句子为空

> 关于第 3 条为什么用绝对台数而不是命中率：这个比例的分母是语料句数，而句数会随车队覆盖的型号与类别数量一起增长。2026-09-13 扩充机型库（挖掘机 5→7 个型号，新增叉车/起重机两个类别）后，句数 41→56、唯一命中 17→22（**能力其实上升了**），比例却从 41% 掉到 39%。用比例当底线，等于把"车队覆盖更全"误判成"解析能力退化"。

#13 是另一种"行为测试抓不到"的缺陷：加了列却没接线，同一个会话内一切正常，只有重启才暴露。因此自检里补了一条**源码结构校验**：`work_orders` / `equipment` / `maintenance_records` 等表的每一列，都必须出现在对应的写库映射函数里。

#17 是最隐蔽的一类：`push` 进数组的普通对象，事后改它的字段不触发任何重渲染。它此前之所以看着正常，是因为模板整个写在一个大组件里，任何别的响应式变化都会让该组件整体重渲染、顺手把最新值重读一遍——**缺陷被架构的粗粒度掩盖了**。拆出子组件后 props 引用不变、子组件不重渲染，问题立刻显形。这类"拆开才暴露"的缺陷，是拆分本身最大的副产品价值。

#19 值得单独记一笔：它出在**守卫自己**身上。扫描器正则写错 → 一条违规都没扫到 → 断言以"全绿"通过。为了不再犯，凡是靠扫描实现的守卫，都先断言"它认得出一段已知的违规写法"，再断言"仓库里没有违规"——**先证明它会响，再相信它没响**。

#14 则暴露了端到端脚本自身的一个盲区：原先"刷新后数据不丢"用的是 `Page.navigate` 到**同一个含 hash 的 URL**，属于同文档导航，压根没重新加载 —— 断言一直是"通过"的，但它验证的东西比名字承诺的少。改用 `Page.reload` 后才真正覆盖。

### #20 #21：自动化验收**结构上抓不到**的一类

上面 19 条几乎都来自自检或端到端，但 #20 与 #21 **不是** —— 两套端到端脚本全绿的情况下，它们依然存在。原因不是脚本写得不够，而是这类缺陷的性质：

- #20 是**对比度**问题：文字和底色的色值各自都是对的，`getComputedStyle` 查出来也"有颜色"。只有把照片和那层半透明药丸一起渲染出来，人眼才知道读不出来。
- #21 是**布局遮挡**问题：DOM 里「复诊」列的元素**存在、可见、文本正确**，任何"元素是否存在/文案是否正确"的断言都会通过。它是被右侧固定列**画在上面**盖住的 —— 这是渲染层的事。

端到端脚本断言的是"数据和交互对不对"，这两条属于"画出来能不能看"。**自动化验收对视觉缺陷是结构性失明的**，所以本次 UI 打磨是靠无头浏览器批量截图后逐张看图抓出来的，不是靠断言抓出来的。

> 结论写在这里以免误读：`npm run verify` 全绿**不等于**界面没问题。视觉这一层目前靠人工过截图，尚未做成自动化（无头截图比对基线是一条可行的路，但阈值调校成本高，本轮未做）。改完界面的自查清单见 [`视觉规范.md`](视觉规范.md) 第五章。

### #22 附：`win-x64-vulkan` **不能**排掉 —— 源码推理与实测相反

打包瘦身时最像"明显冗余"的一项是 `@node-llama-cpp/win-x64-vulkan`（约 99 MB）。读源码确实支持这个判断：

```
getGpuTypesToUseForOption() → [cuda?, vulkan?, false]     // false = CPU，永远是最后一项
getLlama() 按顺序 try/catch，只在最后一项上 rethrow
```

CPU 兜底路径真实存在，排掉 vulkan 程序也不会崩。**于是实测了一次，结论反了** —— 把 `node_modules/@node-llama-cpp/win-x64-vulkan` 临时移走再跑同一段生成：

| 后端 | 生成 128 token 耗时（三次取中位数） | 输出 |
|------|--------------------------------------|------|
| vulkan（本机实际选中） | **450 ms**（438 / 450 / 571） | 正常作答 |
| 退回 CPU（`llama.gpu === false`） | **14580 ms**（10618 / 14580 / 37988） | **退化**：把提示词原样复读了三遍，没有作答 |

慢 **32 倍**，而且不只是慢 —— 演示时那句话会变成一段复读机。移除后 node-llama-cpp 如实打印了 `A prebuilt binary was not found, falling back to using no GPU`，说明兜底确实生效、不会崩；**"能兜底"和"兜底要付多少代价"是两件事**，只看源码会得到一个能让演示现场卡住的"优化"。

所以这 99 MB 保留，并且加了一条断言把它钉住：任何人再"顺手排掉 vulkan"，验收链会红，并直接打印出这个 32 倍的实测结论。**这条断言原先在 `npm run self-check`，2026-09-26 随 #26 的配置改版搬进了 `npm run pack-check`**（判据从"白名单里得有这一行"改成"它不在排除清单里"，结论本身一字未改）。

> 顺带确认了一件没做的事：`node_modules/@node-llama-cpp/win-x64-cuda`（168 MB）与 `win-x64-cuda-ext`（351 MB）合计 519 MB，本机实测两个后端都选中的是 vulkan，说明这台机器走不了 CUDA；为一个 0.5B 模型多背 519 MB 不划算，未纳入。排除方式在 #26 之后从"白名单没有它"变成 `files` 里的三条显式排除项。

> **2026-09-26 补记一条测量陷阱**：上面这个结论**只能在 Electron 里测**。裸 `node` 下 node-llama-cpp 的 binding 自检要另起一个进程，起来后会打印 `Failed to load a prebuilt binary for platform "win" "x64" with Vulkan support, falling back to using no GPU` 并回退 CPU。同一份 `node_modules`，`npx electron` 起来是 `gpu=vulkan`，裸 `node` 是 `gpu=false` —— 差的是运行环境，不是 vulkan 坏了。当天差点据此把这条结论当成过时信息删掉。

### #22 附二：体积降了，不等于还能跑

`files` 从"排除清单"改成"白名单"后 asar 掉到 15.1 MiB（-93%），但**光看体积不足以证明还能跑** —— asar 里少一个包，症状是装到评委机器上点"加载模型"才炸，而 `vite build`、`verify`、自检全都不会响。

所以本轮另外做了一次打包产物的**运行期**验证（`win-unpacked`，不是浏览器模式）：

1. 启动 `release/win-unpacked/矿山智工.exe`，确认窗口渲染、preload 白名单注入（`window.electronAPI.llm` 在）；
2. 走真实路由进「本地模型」页（页面挂载时会自动触发加载），轮询**主进程状态机**直到 `ready` —— 模型加载 4572 ms；
3. 再**真的生成一次**（278 ms），输出《徐工 XE210C 挖掘机的健康分是62，主要扣分项是维保超期18天。》；
4. 断言主进程日志里没有 `MODULE_NOT_FOUND` / `ERR_DLOPEN`。

文件清单只能证明"东西还在"，第 2–3 步才证明"留下的那些**能被解析、能被 require、能真的跑出一段话**"。

> 这里也踩了一次"断言选错对象"：探针最初判断就绪靠的是**页面文案**里出现"就绪"二字且没有"加载中"，结果页面静态文案本来就含"就绪"，探针立刻假通过、当场放行，而真实状态是 `loading`。改成只认主进程返回的 `state` 字段才可靠。**文案会改、会重复出现在别处；状态机不会。**（与 #19「先证明它会响」同源。）

### #23 附：守卫的第一版，断错了不变量

#19 记的是"扫描器正则写错，扫不出东西却全绿"。这次是同一族的另一种形态：新写的打包守卫第一条断言是

```js
files[0] === '!node_modules/**'     // ← 错的
```

它第一次运行就 FAIL（实际首位是 `src/main/**/*`）。**失败的不是仓库，是这个断言**：白名单能成立靠的是"排除项排在放行项之前"，而 `src/main`、`dist` 那几条与 `node_modules` 不重叠，排在前面完全无害。真正的不变量是顺序关系，不是绝对下标。

改对了之后，又补了一次**反向验证**：临时把排除项挪到数组末尾、重跑自检，确认它真的会 FAIL，再还原。

> 这两条合起来的教训：断言写得越像"把当前状态抄一遍"（`files[0]` 就是现在的样子），越容易在实现一变就报假警，或者在坏掉时恰好还成立。写守卫时该问的是"**什么条件下它会红**"，并且真的去造那个条件试一次。

> **2026-09-26 后记**：这条守卫（连同它守护的整个白名单模型）已被 #26 整体替换。有意思的是它的失效方式**恰好证明了上面那条教训** —— 白名单模型本身是"把当前状态抄一遍"的极端形态：它把"现在需要哪三个包"写死在配置里，而真正的需求是"node-llama-cpp 依赖谁"。顺序断言写得再对，也拦不住"清单少列了一个依赖"。现在的判据是算出来的（按真实 `node_modules` 求闭包），不是抄出来的。

### #27 附：占位 spacer 与滚动容器挤在同一个元素上

用户报"设备台账界面无法显示全部设备"。现象和数字：

| 量到的东西 | 缺陷态 | 修复后 |
|---|---|---|
| 容器高 | **4736 px**（= 60 台设备全展开的高度，滚动条几乎没有行程） | 660 px（夹在视口内） |
| 可见卡片 | 恒定 **12 张**，滚到底还是那 12 张 | 21 张/屏，滚动时窗口正常推进（21 → 15） |
| 滚动能摸到的设备 | **18/60**（e2e 实测） | **60/60** |
| 末张卡片 | 永远进不了视口 | 超出容器下沿 1 px |

三个原因叠在一起，缺任何一个都不会出错：

1. **占位 spacer 与滚动容器是同一个 `div`。** 虚拟滚动靠 `padding-top/padding-bottom` 撑出未渲染部分的占位高度，但占位元素自己就是 `max-height` 那个元素。全局 `box-sizing: border-box` 之下，padding 一旦大于 `max-height`，**内容盒被压成 0，元素的实际高度就等于 padding** —— `max-height` 完全失效。修复后的结构把两者拆成两个元素：`.equip-grid.virtual-scroll`（`max-height` + `overflow-y`）包着 `.equip-grid-inner`（承载 padding 占位 + flex 换行）。
2. **视口高用 `ResizeObserver.contentRect.height`。** 它**不含 padding**，于是容器量出来是 0，可见行数算成 0/负数，渲染窗口永远停在首屏、再也不更新。改成 `entry.target.clientHeight` 并加 `> 0` 守卫（量不到就退回 CSS 估值，而不是把窗口算成空）。
3. **行高/列数按 CSS 里的估值写死**（`cardHeight: 280`、`cardMinWidth: 300`）。这种写法的失效方式很隐蔽：卡片换个内边距，占位高度就和真实高度错位，滚动条拖到底会露出一截空白或截掉一行 —— 而上面的三条断言照样全绿。改成给了 `itemSelector` 就按**真实 DOM** 量（同一 `top` 的卡片刻数 = 列数，首卡高度 + gap = 行高），CSS 怎么漂移都不会错位。

**这一节真正该记的是断言那一侧**：e2e 里原本就有断言覆盖这张表，写的是

```js
cards >= 1 && cards <= 60     // ← 配注释"首屏约 12 张"
```

它把缺陷的**症状写成了预期行为** —— 12 张在 1..60 区间里，全绿。放回缺陷时实测红：`可达 18/60 台`（因为偶尔能多滚一屏）。三条新断言是：滚到的**去重**设备名必须 60 台、容器高必须夹在 `> 200` 且 `<` 视口高之间、末张卡片必须进视口。

**扫描方法上踩了一个坑**：写"滚到 60 台"时最初用一次性 `grid.scrollTop = grid.scrollHeight`，实测报 **36/60** —— 这个赋值只走首屏和末屏两个窗口，中间全跳过。改成"一次一个视口地走"（`scrollTop += clientHeight`，最多 40 步，每步等一帧 + 80 ms）才是真的 60/60。**断言变红了，但红的原因是扫描方法不对，不是产品缺陷** —— 与 #25 后记、上面那条"没验成"的变异是同一类错误。

> 相关但**未改**的既有问题：`.el-main` 实测 911 px / 884 px 有 27 px 溢出，来自 `el-card` 的下边距。台账容器本身是贴合的（top 266 / bottom 926，窗口高 940），`calc(100vh - 280px)` 这个估值偏宽松约 27 px。与本次报障无关，如实记录、不在本次改动范围内。

- **案例库**：浮层里写的是 `v-if="detailKind === 'sample' && detail.text"`，而 `utils/faultStats.js` 造样本行时只 push 了 `title/source/id/equipmentName/date` —— **没有 `text` 字段**。死代码，浮层里一个字正文都没有。而断言只查「设备/日期」两个标签在不在，照样全绿。

两种写法错在同一件事：**断言描述的是界面的"形状"，不是用户点开之后要看到的内容**。改法是把界面上的东西拿来做比对 —— 行里那段被截断的原话必须出现在详情正文里；规程详情的"原因/处置步骤"必须真的列出条目（`li` 数 ≥ 2），光有几个空标题不算。改完把缺陷放回去实测变红，诊断是「行内原文「液压油压力偏低，动作无力」→ 详情里没有」。

> 这一条与 #19、P2-7 的"扫描陷阱"、P2-8 的"前提选错"同源：**先确认它是红在你以为的那件事上**；同样是绿，也要问一句"这个绿是因为对了，还是因为根本没验到"。

### #30 附：老师傅模式"开了没法对话"，根因在意图判定而不在人设层

用户报「老师傅模式开启后没有启动以及无法交互对话」，一起报的还有「聊天记录总是回滚到最前面」。前者的根因**不在** `masterPersona.js`（人设、开场白、提醒都在，开关也真的写进了 localStorage），而是这一层：一线问的是「回转马达异响怎么回事」「水温高咋回事」这类口语疑问句，而 `QUERY_PATTERNS` 那十条句式偏书面，一个都不命中 —— 于是掉进"提到故障关键词就报修"的兜底，用户看到的是「我识别到你要**登记一条运维记录**」的写库确认卡。**问现象变成了报修，看起来就是"开了没法对话"。**

### #31 附：一条"永远绿"的断言 —— 出处非空 ≠ 答对了问题

2026-09-26 接着 #30 那条"未改"的记录做检索排序，缺陷在探针里复现得干干净净：录完本地规程《XE215C 回转马达异响排查》后问**「回转马达异响怎么回事」**，出处是两页手册原文 + 《发动机异响》，刚录的那条被挤到第 4 名、被 `limit=3` 截掉；同一件事多说一个机型（「XE215C 回转马达异响怎么处理？」）就正常 —— **用户多说一个词就换一个答案**。

根因在打分而不在流程：手册正文分封顶 8，注释写明"不会让手册原文顶掉更对症的精选知识条目"，但这个上限只挡住了**标题命中**（+12）那一路；只命中关键词的精选条目是 3+3 = 6 < 8。（详见 `docs/完善计划.md` P2-14。）

**这一轮真正值得记的是断言那一侧**：新加的那条 e2e 断言——"命中出处里必须有刚在上一段录入的那条规程"——是**先红后绿**的（`npm run build && npm run e2e` → 150 项 1 项失败，refs 原样打印出两页手册原文与《发动机异响》）。而它旁边原来那条断言当时是**绿的**：

```
check('老师傅模式下问故障现象能命中本地规程/排查思路（不是一句"查不到"）',
  !masterAsk.error && (masterAsk.refs || []).length > 0 && !/查不到|没有检索到/.test(...))
```

它只要求"refs 非空"。而 refs 非空**只说明检索到了东西**，不说明检索到的是**你问的那个东西** —— 引用一本别的机型的手册同样算"有本地出处"。这与 #29 附那两种写法同源（描述形状而不是描述内容），但更隐蔽：`else` 兜底与"只看标签名"至少还看得出少验了一层，这一条看上去是在验"能不能命中"。

改法：断言换成**拿界面上已有的那条数据做比对** —— 上一段刚录入的规程标题必须出现在本条的出处里（`refs.some(r => r.includes('回转马达异响排查'))`），不再满足于"有出处"。同时 self-check 补一条纯排序断言：混合池（精选 31 条 + 随包手册 86 片，字段与 `appStore.answerItems` 逐项对齐）里，提问直中两个以上关键词的精选条目必须排在手册原文之前 —— 改前红，诊断给出 `首位=《XCA60E…》第 4 页；前三=…(8) > …(8) > 发动机异响(7)`。

### #32 附：断言"改前就是绿的"不等于它没用 —— 但必须证明它在该坏的时候会坏

顺着 #31 那条排序断言往下做（P2-15），同一块池子上又加了两条守卫：**代号只对它自己那本手册生效**、**点了代号也仍按正文选页**。两条在改之前就是绿的 —— 按"每条新断言都要做能失败验证"的纪律，这是个必须回答的问题：**它们是真守着什么，还是只是碰巧是绿的？**

答案只能靠变异：把实现往这两个守卫各自防的方向改坏，看断言会不会红。

| 变异 | 守卫断言的反应 |
|------|----------------|
| 代号规则改成"见码就加分、不看这码是不是这本手册的" | ❌ 红：`QY25K5D 问 → XCA60E 手册 ｜ XCA60E 问 → XCA60E 手册`（两个提问双双落到同一本手册） |
| 把正文分临时清零（模拟"整本手册所有切片同分"） | ❌ 红：`支腿液压锁 → 第 1,2,3 页 ｜ 最大起重量 → 第 1,2,3 页` —— 报出的正是"页码与提问内容无关"的退化 |

第二条尤其值得记：`第 1,2,3 页` 这个诊断**自己就把结论说清楚了**（正文分一旦不参与，元数据分对同一本手册的所有切片完全相同，稳定排序就退化成文件顺序）。而这恰好是 `scoreByContent` 当初存在的理由 —— 守卫断言把它写成了可执行的形式。

**所以纪律补一句**：新增断言改前是红的，直接观察即可；改前是绿的，就必须**指出它防的是哪种写法，并把那种写法学着写一遍**（变异），证明它会红。两条都做不到的断言，按占位处理。

### #33 附：断言"把要断言的值自己写掉了" —— 读在还原之后

P2-16（台账白屏）的 e2e 断言第一版是这么写的：

```js
grid.scrollTop = 0                    // 还原：把容器滚回顶部
grid.dispatchEvent(new Event('scroll'))
return { ok: true, 深处: deep, 筛选后: filtered, 重开后: after }   // after 在这之后才求值
```

`after` 是个对象字面量，**它在"还原"那一步之后才求值** —— 于是 `after.dom滚动位置` 读到的永远是刚刚写进去的 `0`。断言写成 `重开后?.dom滚动位置 === 0`，从此**不管应用有没有真的回到顶部，它都是绿的**。这条断言当时的"通过"，和 #31 是同一类：**断言自己把自己要观察的现象抹掉了**。

改法是先量后还原：把 `const after = {...}` 挪到 `grid.scrollTop = 0` **之前**。改完立刻见红 —— 改前两个环境都停在深处（e2e `5521px`、探针 `5659px`）。

**判据补一句**：一条断言里只要有"把被测对象恢复原状"的收尾动作，就必须确认**所有读取都发生在收尾之前**。这类错误不会报错、不会警告，只会让断言永远绿。

### #34 附：开发态永远看不见的一类 —— 换个 URL 方案才现形

P2-17（设备照片）的照片路径写的是根绝对 `/equipment-photos/x.jpg`。开发态页面是 `http://localhost:5173/`，它解析成 5173 下的路径，**一切正常**；e2e 走的也是这一种，所以 e2e 全绿、人过截图也看不出问题。

打包版不同：`mainWindow.loadFile(dist/index.html)`（`src/main/index.js:486`）⇒ 页面 URL 是 `file://`，同一串按 URL 规范解析成 **`file:///D:/equipment-photos/x.jpg`** —— 盘符根目录。**装完包，5 处界面的设备照片全碎**（设备台账卡 / 设备档案 / 告警中心 / 看板 / 设备记录）。

这和第五节"尚未覆盖"表里记的 `EPERM`（#28）是**同一类**：只有"真 Electron 运行时"这一层才现形，`verify` 链（浏览器模式）结构上看不见。本轮的做法是先用一个**只做 URL 解析**的静态页把机制钉死（`file://` 页 + 与应用一致的 CSP：`/equipment-photos/excavator.jpg` 解码宽 **0**、`./equipment-photos/excavator.jpg` **1365**），再用 `electron-builder --dir` 的 `win-unpacked` 真机跑一次，在**同一个运行时**里现场对照新旧两种写法（旧 `error` / 新 1365），并截图人工确认。

**断言写法上的一个连带收获**：原 e2e 的照片断言是"卡片数 === `src` 匹配 `/equipment-photos\/.*\.jpg/` 的卡片数"。碎图的 `src` **一样匹配**，而 `img.complete` 对**加载失败**的图也是 `true` —— 也就是说"有 `<img>`"被当成了"图能显示"。现在要求 `naturalWidth > 0`。这两件事在开发态几乎总是同时成立，所以这个区别平时看不出来。

### #35 附：一处**能把自己变成"没有输出"**的断言写法（P4-1 变异验证时抓出）

P4-1 的变异 M2 是把 `verifyPin()` 改成恒返回 `true`（PIN 校验没接上、锁形同虚设）。放回去之后，**整轮 e2e 直接中断**：181 条断言一条都没打印，只剩一句

```
TypeError: Cannot read properties of null (reading 'click')
    at scripts/e2e.mjs:2273
```

根因不在变异，在测试写法：那条断言里是

```js
document.querySelector('.lock-btn').click()   // 锁屏消失 ⇒ 这个选择器是 null ⇒ 抛异常
```

这是**裸点击**。而 e2e 的主流程外面是 `main().catch(e => console.error(e))` —— 异常一路冒上去只打一句错误，**汇总表不打印、已收集的断言全部丢失**。也就是说：一个真实的严重缺陷（锁形同虚设），在这套测试里的表现不是"若干条断言变红"，而是"看起来像环境问题、没有任何断言输出"。**一个能被缺陷变成"没有输出"的测试，比一条会变红的断言差得多。**

修法：把点击收敛成注入页面的 helper，元素缺失时**不抛异常，而是返回一句可断言的诊断**：

```js
window.__unlock = async (pin) => {
  const input = document.querySelector('input[placeholder^="PIN"]')
  const btn = document.querySelector('.lock-btn')
  if (!input || !btn) return { ok: false, why: '锁屏不在（没有 PIN 输入框或解锁按钮）' }
  ...
}
```

再把这个 `why` 串带进断言。改完重跑同一个 M2，得到的是 **3 条各带精确诊断的红**（`提示「」/ 仍锁=false / isReady=true`、`输入框残留「(没有输入框)」`、`锁屏不在（没有 PIN 输入框或解锁按钮）`），其余 178 条照常跑完并打印。同一个缺陷，从"整轮没输出"变成"3 条指名道姓"。

> 这与 #29（合成事件替真实鼠标事件背书）和 P3-3 那条 `feedFile` 守卫是同一类：**测试里凡是"假设某元素一定在"的写法，都要么加前提断言、要么降级成可断言的诊断**。断言可以红，但不能消失。

**同一个坑的第二种长相（P4-2 变异验证时又踩到一次，2026-09-27）**：这次不是"元素不在"，而是**函数不在**。

P4-2 的空闲自动锁到点走的是 `location.reload()`，所以注入到 `window` 上的 helper 会**随页面一起消失**。变异 M7（把活动监听全去掉 ⇒ 60 秒就该锁 ⇒ 到第 82 秒那次求值时页面早已刷新过）第一跑得到的是：

```
TypeError: window.__pickIdle is not a function
```

**整轮 e2e 又只留一句话、190 条断言全部丢失。** 元素不在与函数不在，是同一条纪律的两个面：注入型 helper 的**寿命**也是前提之一，而 P4-2 引入的 `location.reload()` 恰好让这个寿命变得不确定。

修法是加一层 `withLockHelper(expr)` —— **每次用之前重新注入一次**。注入是幂等的（只是重新定义几个 window 函数），而且**不会掩盖缺陷**：页面若已回到锁屏，`__pickIdle` 自己会返回「设置页没有「空闲自动锁」那一行」，比一句 TypeError 有用得多。改完重跑 M7，得到 4 条各带精确诊断的红（`此刻锁屏在=true`、`设置页没有「空闲自动锁」那一行`、…）。

**变异顺带抓出的另一处：断言之间不该有隐含的前提依赖。** 收尾那条原本无条件调 `__unlock`，于是 M8（计时器写死不重读阈值 ⇒ 从没锁过 ⇒ 根本没有锁屏）一红，它跟着红成"锁屏不在（没有 PIN 输入框或解锁按钮）"，看着像两处坏了、其实只有一处。改成"锁屏在就解锁、不在就直接收"，职责收回到"别把锁留着"本身。**一条断言如果会因为上一条的失败而失败，它给出的信号就是噪声。**

## 四、验收设计原则

1. **一条命令跑到底**。原本 e2e 要求"另开一个终端先跑 `npm run dev`"，导致 `npm run verify` 永远跑不到最后两步就退出 —— 一个需要人工介入的验收等于没有验收。现在脚本自带开发服务器（外部已起着就复用，跑完不动别人的进程）。
2. **断言要能抓到"静默失效"**。最危险的 bug 不是崩溃，而是"看起来正常但结果不对"（#4 #5 #6 #8）。因此对账类断言（件名 100% 可在台账查到、带配件记录费用不为 0、刷新前后一致）比功能断言更重要。
3. **不猜就是正确**。歧义场景下"返回候选并拒绝写入"是**预期通过**，不是失败。
4. **数字不变量必须校验**。本地模型生成的文本，其数字必须是规则引擎结论数字的子集，否则整段丢弃 —— 这条也在自检里作为纯函数断言覆盖。
5. **先确认它真的在测那件事**。这条是从四次实测里逼出来的：P2-7 的扫描陷阱（`scrollTop = scrollHeight` 只看到首屏与末屏，报 36/60）、P2-8 的前提取错（被删档位本就不会被重选，缺陷放回去照样全绿）、P2-2 的两次"断言不合格"（先写成恒真，改了以后仍被另一处落盘抵消）、以及 §六 那条压测假绿（`answerItems` 从没读过知识条目的属性，改标题并不能让它失效，量到 0.0 ms 的缓存命中）。四种错误的表象都是"跑出来了、有数字、是绿的"，共同点是把**测量/断言的前提**当成了显然成立。落法：能给前提本身加一条检查就加（压测里那条"还是同一个数组引用就报警"），加不了就至少先做一次**能失败**的验证。

## 六、单机规模压测（`npm run bench:scale`，**不进** `verify` 门禁）

十套验收脚本回答的都是"对/不对"，没有一条回答"5000 台设备、5 万条维保记录时它还转得动吗" —— 这一层此前完全没有基座（`docs/完善计划.md` P2-5）。**它不进 `verify`**：耗时测量不是断言，机器繁忙时的抖动不该让整条验收链变红（#28 那条教训的另一面）。

做法与 `store-check` 同源：把 `utils/`、`stores/` 镜像成 ESM，在 Node 里真正装配 pinia + sql.js，再**走真实写入路径**灌数据（`addEquipment(silent)` / `addMaintenanceRecord(silent)`），不是造一个假的压测模型。

**本机实跑 2026-09-27**（Windows 11 / Node v24.16，5000 台设备 + 5 万条维保 + 手册语料 8 本 × 300 片，每项 5 次取中位）：

| 场景 | 中位 | 最小 / 最大 |
|------|------|-------------|
| 首启（空库 → 播种 60 台） | 8.4 ms | 7.9 / 8.9 |
| 满库首启（读回 5000 台 + 5 万条并重建内存态） | 246.0 ms | 242.0 / 271.0 |
| 看板（健康分 + 分档 + 超期 + 预警重算） | 55.7 ms | 55.5 / 68.5 |
| 检索·池重建（`answerItems`） | 2.2 ms | 1.9 / 2.6 |
| 检索·一次提问（打分，池已缓存） | 20.3 ms | 18.7 / 23.4 |
| 落盘·一次真实用户写入（含整库重写） | 107.6 ms | 107.0 / 109.3 |
| 落盘·整库序列化（`db.persist(force)` → `export()`） | 23.5 ms | 19.5 / 24.3 |
| 批量灌数·新建设备 | 0.33 ms/台（5000 台合计 1.65 s） | — |
| 批量灌数·维保记录 | **0.235 ms/条**（5 万条合计 11.7 s） | — |

**参照跑**（同一天，1000 台 / 1 万条）：满库首启 66.7 ms、看板 10.7 ms、维保记录 0.054 ms/条、检索那两条与上面**基本一致**（池子规模由手册语料决定，与台数无关）。

**两条量出来的结论（不是推演）**：

1. **维保记录的批量导入是超线性的**：1000 台时 0.054 ms/条 → 5000 台时 0.235 ms/条，台数 ×5、单条成本 ×4.4 ≈ 线性于台数，合计即 **O(台数 × 记录数)**。原因是 `addMaintenanceRecord` 每条都要 `equipmentList.find(e => String(e.id) === key)` 定位设备。Excel 导入走的正是这条路（`importFromExcel` 逐行调它，`appStore.js:1222`），所以"导入一张 5 万行的维保表"在 5000 台车队上要 12 秒。**演示规模（60 台）完全无感**：同样一条 5 万行表在 60 台下是 0.005 ms/条 × 5 万 ≈ 0.25 秒。
2. **检索成本随手册语料增长，不随车队增长**：台数从 1000 加到 5000，检索那条 20 ms 一动不动；换成 2430 条的池子（8 本 × 300 片）后，**建池约 2 ms、打分约 20 ms** —— 花在打分的占九成，这正是 `docs/完善计划.md` P2-3 要动的那一处。

**一处测量陷阱（如实记录，脚本第一版就踩了）**：压测第一版量"池重建"量出来 **0.0 ms**，看上去像"建池不要钱、20 ms 全在打分"，结论**正好反了**。原因是 Vue 的 computed 只追踪**它读过的东西** —— `answerItems` 里那句 `const base = [...knowledgeItems.value]` 只迭代数组（读 length 与下标），从没读过条目的任何属性，所以"改一下知识条目的标题让它失效"根本没让它失效，量到的是缓存命中。真正能失效它的是文档那一侧（逐片读了 `doc.status` / `chunks` / `chunk.page` / `chunk.text`）。

> 脚本里现在有一条**测量前提检查**盯着这件事：碰完数据后 `answerItems` 如果还是同一个数组引用，就直接打印"这一列量到的是缓存、先修 `invalidatePool`"。与 P2-7 的扫描陷阱（跳 `scrollHeight` 只看到首屏与末屏）、P2-8 的"前提选错、断言成了摆设"是同一类错误：**先确认它真的在测那件事**。

**这一层结构上抓不到什么（如实说明）**：跑在 Node 的 harness 里，`db.persist()` 的**存储后端是桩**（没有 indexedDB、localStorage 是个 Map），所以"整库序列化"那 23.5 ms 是真的（`db.export()` 真的导出了整库字节），但**真机上还要加上 IPC + 写 `userData/*.db` 的时间**，这一段没有量到。同理，DOM 渲染耗时（60 台虚拟滚动 vs 5000 台）也不在这里 —— 那要真实浏览器，属 e2e 与人工截图的范围。

## 七、复现步骤

```bash
npm install
```
